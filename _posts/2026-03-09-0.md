## 들어가며

**"지금 내 서버는 최대 몇 명까지 쾌적하게 플레이할 수 있을까?"**

최근 poposafari에 실시간으로 다른 유저의 움직임이 보이는 기능을 새롭게 추가하면서, 자연스럽게 생긴 궁금증이었습니다. 이 기능에 대해서 조금 자세하게 말씀 드리자면, 유저가 이동할 때마다 서버가 같은 맵의 모든 유저에게 위치를 브로드캐스트하는 것인데, 유저 수가 늘어날수록 서버가 처리해야 할 브로드캐스트도 늘어나기 때문에 이 구조가 어디까지 버틸 수 있는지가 궁금했습니다.

이 궁금증을 시작으로 부하 테스트를 진행했고, 그 과정에서 CPU를 잡아먹는 구조적 문제를 발견했습니다. 이번 글에서는 이 원인을 추적하고, Batch Packet Sending을 적용해서 CPU 사용량을 절감한 경험을 공유하고자 합니다.

## 기존 구현 방식

`socket.io` + `Node.js` 조합으로 구현을 한 상태였고, 유저의 실시간 상태는 Redis Hash(`user:{authId}:state`)로 저장하고 있었습니다.
클라이언트로부터 `move` 이벤트가 수신될 때,

1. `getUserState`로 Redis에서 해당 유저의 현재 상태를 조회
2. `direction`과 `moveType`에 따라 새로운 좌표를 계산
3. `updateUserStatePosition`으로 Redis에 변경된 좌표를 저장
4. 같은 방(`roomId`)에 있는 모든 유저에게 `user_moved` 이벤트를 브로드캐스트

이런 로직이 수행됩니다.

```typescript
// Redis 키: "user:{authId}:state"

export async function getUserState(authId: string): Promise<UserState | null> {
  const key = `user:${authId}:state`;
  const raw = await RedisClient.hgetall(key);
  if (!raw || Object.keys(raw).length === 0) return null;
  return toUserState(raw);
}

export async function updateUserStatePosition(
  authId: string,
  updates: { x: string; y: string; lastMoveTime: string },
): Promise<void> {
  const key = `user:${authId}:state`;
  await RedisClient.hset(key, updates);
}
```

```typescript
socket.on("move", async ({ direction, moveType }) => {
  // ... 유효성 검사 생략

  // 1. Redis에서 현재 상태 조회
  const state = await getUserState(userId);
  if (!state) return;

  // 2. 새 좌표 계산
  let { x, y } = state;
  const step = moveType === "jump" ? 2 : 1;
  switch (direction) {
    case "up":
      y -= step;
      break;
    case "down":
      y += step;
      break;
    case "left":
      x -= step;
      break;
    case "right":
      x += step;
      break;
  }

  // 3. Redis에 상태 저장
  await updateUserStatePosition(userId, { x, y, lastMoveTime: now });

  // 4. 같은 방 유저에게 브로드캐스트
  this.io.to(roomId).emit("user_moved", { userId, x, y, direction, moveType });
});
```

## 부하 테스트 설계

### 부하 테스트의 목적

아직까지 "내 서비스는 몇명까지는 받고 싶다!"라는 목표치가 없었기 때문에, **적어도 지금 내 서비스는 몇명까지는 쾌적하게 플레이할 수 있다**라는 기준점이 필요했습니다.

이 기준점을 잡기 위해 부하 테스트를 진행하고, 그 결과를 바탕으로 아래 흐름을 따라가 보려고 합니다.

1. **서버 한계 파악** — 지금 인프라(미니PC 4코어, Node.js 싱글 스레드)에서 같은 맵에 동시 접속한 유저가 몇 명일 때까지 쾌적한 플레이가 가능한지 확인한다.
2. **병목 지점 식별** — CPU 사용량이 한계에 도달했을 때, 서버 코드의 어떤 부분이 가장 많은 CPU를 소비하고 있는지 찾는다.
3. **개선 및 검증** — 병목을 해소할 수 있는 구조적 변경을 적용한 뒤, 동일한 조건에서 다시 테스트하여 개선 효과를 확인한다.

### 서버 환경

개발 환경의 경우에는 맥북 프로(M1)을 사용하고, 스테이징 환경은 집에 있는 미니PC를 사용하고 있습니다.

`lscpu` 결과를 보면, 제 미니PC는 코어가 총 4개이고 각 코어당 스레드(Thread)는 1개입니다. 이 4코어 위에서 여러 컨테이너가 함께 돌아가고 있기 때문에, 부하 테스트에서 측정하는 CPU 범위를 명확히 해둘 필요가 있었습니다.

제 소켓 서버는 `Node.js`이기 때문에, 메인 스레드는 단 1개입니다. 그러므로, 제 미니PC 기준에서는 `Node.js`의 메인 스레드는 물리 코어 1개만 사용할 수 있습니다.

### 테스트 시나리오

**서버 한계 파악**이라는 저의 목적을 달성하기 위해서는 CPU가 받을 최악의 상황을 가정하는 것이 알맞는 시나리오라고 생각했습니다. 아래 시나리오로 구성하고자 합니다.

1. N명을 하나의 맵에 전부 접속 시킨다.
2. N명이 각각 클라이언트 기준 최고의 속도로 무작위 방향으로 X번 이동한다.(`move` 이벤트를 계속 쏜다.)

2번을 만족시키기 위해서는 `init`이라는 소켓 이벤트를 반드시 거쳐야 했습니다. 왜 그런지 서버 코드를 보면 알 수 있습니다.

제 서버의 `init` 핸들러는 DB에서 유저 정보를 조회한 뒤, Redis에 `UserState`(좌표, 닉네임, 코스튬 등)를 캐싱하고, Socket.IO 방에 참여시키고, 마지막으로 `socket.data`에 `userId`와 `roomId`를 저장합니다.

```typescript
// apps/socket/app.ts — init 핸들러 (핵심 부분)
socket.on("init", async () => {
  // 1. DB에서 유저 정보 조회
  const user = await userRepo.findOne({ where: { authId } });

  // 2. Redis에 UserState 캐싱 (x, y, mapId, nickname, costume, lastMoveTime 등)
  await setUserState(authId, {
    mapId, x, y, nickname, costume, socketId, gender, pet, createdAt, lastMoveTime,
  });

  // 3. Socket.IO 방 참여 + 방 멤버 목록에 추가
  await socket.join(mapId);
  await addRoomMember(mapId, authId);

  // 4. socket.data에 userId, roomId 저장
  data.userId = authId;
  data.roomId = mapId;

  // 5. 클라이언트에 init_ok 응답
  socket.emit("init_ok", { userId: authId, ... });
});
```

그리고 `move` 핸들러의 첫 줄을 보면, `init`이 선행되지 않으면 `move`가 아예 동작하지 않게 됩니다.

```typescript
// apps/socket/app.ts — move 핸들러
socket.on("move", async ({ direction, moveType }) => {
  const { userId, roomId } = socket.data;

  // init을 거치지 않으면 userId, roomId가 undefined → 여기서 바로 return
  if (!userId || !roomId) return;

  // Redis에서 현재 좌표 조회 (init에서 캐싱한 UserState)
  const state = await getUserState(userId);
  if (!state) return;

  // ... 좌표 계산, Redis 업데이트, broadcast ...
});
```

`socket.data.userId`와 `socket.data.roomId`는 **`init` 핸들러에서만 설정**됩니다. `init`을 거치지 않은 소켓은 이 값이 `undefined`이기 때문에, `move` 핸들러가 첫 번째 `if` 문에서 즉시 `return`합니다. 에러 메시지도 없이 조용히 무시됩니다. 그리고, `move` 이벤트가 `getUserState(userId)`로 Redis에서 현재 좌표를 조회하는데, 이 데이터 역시 `init`에서 캐싱한 것이므로 `init` 없이는 조회할 데이터 자체가 존재하지 않습니다.

하지만, `init`과 `move`가 섞여서 동시에 진행되면, 나중에 CPU 수치를 확인할 때 이 수치가 `init` 때문인지 `move` 때문인지 구분할 수 없게 됩니다. 그래서 테스트를 두 단계로 나누기로 했습니다.

1. 1 단계: 모든 유저가 connect + init 완료될 때까지 대기
2. 2 단계: 모든 유저가 동시에 move 시작

N명의 유저가 한꺼번에 `connect`이나 `init`을 수행한다면, 서버가 순간적으로 N개를 동시에 처리해야 합니다. `init`은 Redis 캐싱 + DB 조회를 수행하는 작업이기 때문에, 동시에 몰린다면 `init` 자체가 느려지거나 타임아웃이 발생할 수 있었습니다. 그래서 연결 사이에 딜레이를 두어서 `init` 부하를 줄일 수 있도록 해야 합니다.

그리고 모든 유저가 `init_ok`을 받았어도, Redis 작업이나 Node.js 이벤트 루프에 콜백이 남아 있을수도 있기 때문에, 잠시 대기 한 뒤에 `move`를 시작하는 것이 좋아보였습니다.

결국, 필요한 테스트 시나리오 변수는 아래와 같았습니다.

- **동시 접속자 수(N)**: 같은 맵에 몇 명이 있는가
- **이동 간격(THINK_MS)**: 유저 1명이 몇 ms마다 이동하는가
- **유저당 이동 횟수(MOVE_COUNT)**: 테스트를 얼마나 오래 돌릴 것인가
- **이동 방향**: 랜덤 방향('up', 'down', 'left', 'right')
- **연결 간 딜레이(STAGGER_MS)**: `init` 요청 딜레이
- **안정화 대기(SETTLE_MS)**: `move`를 언제 시작하게 할 것인가

#### 이동 간격(THINK_MS)은 얼마로 둘까?

이동 간격이 짧을수록 서버에 `move` 이벤트가 더 자주 날아가게 됩니다. 그렇다면 이 값을 얼마로 설정해야 제 프로젝트 상황과 가깝게 테스트가 될까요? 너무 느리면 실제 부하를 재현하지 못하고, 너무 빠르면 실제로는 불가능한 속도로 부하를 거는 셈이 됩니다.  
클라이언트 로직에서는 유저가 한 타일을 이동할 때마다 `move` 이벤트를 한 번 `emit`합니다. 즉, **한 타일 이동에 걸리는 시간 = move 이벤트 전송 간격**이 된다는 소리입니다.

```typescript
// src/feats/overworld/overworld.ui.ts
private emitMoveToServer(dir: DIRECTION): void {
  if (dir === DIRECTION.NONE) return;

  const socket = this.scene.getSocket();
  if (!socket?.connected) return;

  const moveType = user ? toMoveType(user.getOverworldMovementState()) : 'walk';
  socket.emit('move', { direction: dir, moveType });
}
```

그리고 이동 타입(걷기(walk), 뛰기(running), 자전거 타기(ride))별로 한 타일을 이동하는 데 걸리는 시간(ms)이 다르게 정의되어 있습니다.

```typescript
// src/feats/overworld/overworld-socket.types.ts
export const MOVE_TYPE_DURATION_MS: Record<string, number> = {
  walk: 288,
  running: 144,
  ride: 96,
  surf: 144,
  jump: 384, // 2타일 이동해서 타일당 192ms
};
```

| 이동 타입 | 한 타일 이동 시간 | 초당 move 이벤트 |
| --------- | ----------------- | ---------------- |
| walk      | 288ms             | ~3.5회           |
| running   | 144ms             | ~6.9회           |
| **ride**  | **96ms**          | **~10.4회**      |
| surf      | 144ms             | ~6.9회           |

서버 입장에서 가장 부하가 큰 상황은, 모든 유저가 가장 빠른 이동 타입으로 계속 움직이는 경우일 것이고, **ride의 96ms를 이동 간격으로 설정**하기로 하였습니다. 이렇게 하면 유저 1명이 초당 약 10회 정도의 move 이벤트를 보내게 되고, 실제 클라이언트에서 발생할 수 있는 최악의 상황이 만들어지는거죠.

#### 동접자가 중요한건가? 걸음 수가 중요한건가?

처음에는 동접자 수와 이동 횟수를 테스트 변수로 두고 테스트를 진행하려고 했었습니다. 동접자 수가 늘어나면 늘어날수록, `user_moved` 이벤트로 브로드캐스트 해야 하는 횟수가 많아져 CPU가 더 많은 일을 하게 될 것이고, 이동 횟수도 마찬가지로 늘어날수록 서버가 처리할 move가 많아지니까, CPU 부하를 측정할 수 있을 것 이라고 생각이 들었습니다.

하지만 이동 간격(`THINK_MS`)의 경우 96ms로 고정되어 있기 때문에, **이동 횟수를 아무리 올려도 초당 서버가 처리하는 move 수는 동일**하였습니다.

```
THINK_MS=96, N=100 일 때

100보: 96ms마다 1회 × 100명 = 매 초 1,000회 move → 10초간 진행
500보: 96ms마다 1회 × 100명 = 매 초 1,000회 move → 50초간 진행
```

바뀌는 건 **테스트 지속 시간**뿐이지, 매 초 서버가 하는 일의 양은 같았습니다.

결국에는 CPU 사용률을 올릴 수 있는 변수는 **동접자 수(N)**라는 말입니다. 서버는 move 1건마다 같은 방의 N명 전원에게 broadcast하므로, N이 올라가면 초당 move 수와 건당 broadcast 수가 곱해져서 **O(N²)**으로 부하가 커집니다.

```
 50명: 매 초  500 move ×  50명 broadcast =   25,000 패킷/s
100명: 매 초 1000 move × 100명 broadcast =  100,000 패킷/s
200명: 매 초 2000 move × 200명 broadcast =  400,000 패킷/s
```

```
N          = 10 -> 50 -> 100 -> 150 -> 200
THINK_MS   = 96
MOVE_COUNT = 300
STAGGER_MS = 1000 (연결 간 1초 딜레이)
SETTLE_MS  = 5000 (init 완료 후 안정화 대기)
```

### 테스트 도구 선택

이번 테스트를 통해서 제가 측정하고 싶은 지표는 두 가지였습니다.

- 시나리오대로 테스트를 돌렸을 때, 소켓 서버의 **CPU 사용량**
- 유저 A가 `move`를 보냈을 때, 같은 방의 다른 유저 B, C, D가 `user_moved`를 제대로 수신했는지에 대한 **broadcast 수신율**

부하 테스트 툴로는 `k6`와 `Artillery`가 많이 사용되고 있다고 구글이 알려주니, 두 가지 모두 검토해 보았습니다.

#### k6

`k6`는 Go 언어로 작성된 부하 테스트 툴로, JS로 테스트 스크립트를 작성할 수 있습니다. 하지만 `k6`는 순수 WebSocket만 지원하고, Socket.IO 프로토콜은 지원하지 않습니다. Socket.IO는 WebSocket 위에 자체 핸드셰이크와 패킷 포맷을 얹은 프로토콜이기 때문에, 순수 WebSocket 클라이언트로는 `emit`이나 `on` 같은 Socket.IO API를 사용할 수 없습니다. k6 공식 GitHub에서도 이 문제에 대한 [이슈](https://github.com/grafana/k6/issues/1306)가 논의되었지만 해결되지 않은 채 남아 있어, `k6`는 제외했습니다.

#### Artillery

`Artillery`는 Node.js 기반이라 Socket.IO 엔진을 내장하고 있고, [Socket.IO 공식 문서](https://socket.io/docs/v4/load-testing/)에서도 Artillery를 활용한 부하 테스트 방법을 안내하고 있어서 가장 유력한 후보였습니다.

Artillery의 Socket.IO 테스트는 `emit` -> `response` 패턴을 기반으로 동작합니다. VU(가상 유저)가 이벤트를 `emit`하고, 같은 VU가 응답 이벤트를 `response`로 수신하면 타이머를 멈춰서 RTT를 측정하는 구조입니다.

```yaml
- emit:
    channel: "move"
    data: { direction: "right", moveType: "running" }
  response:
    channel: "user_moved" # ← 발신자 본인도 수신하니까 동작은 함
```

제 서버는 `this.io.to(roomId).emit()`으로 발신자를 포함한 모든 유저에게 broadcast하기 때문에, 본인이 보낸 `move`에 대한 `user_moved` 응답을 본인이 받는 것 자체는 가능합니다.

하지만 제가 측정하고 싶은 핵심 지표는 **"유저 A의 move가 다른 유저 B, C, D에게 도착했는가"**였습니다. Artillery에서 각 VU는 독립적으로 실행되기 때문에, 다른 VU가 보낸 broadcast를 수신하고 그 수신율을 집계하는 것이 불가능했습니다. Artillery GitHub에서도 이 문제에 대한 [질문](https://github.com/artilleryio/artillery/issues/170)이 올라왔지만, 해결되지 않은 채 남아 있었습니다.

#### 직접 구현

결국 기존 툴로는 제가 원하는 지표를 측정할 수 없었기 때문에, `socket.io-client`를 사용해서 테스트 코드를 직접 작성하기로 했습니다. Socket.IO 공식 문서에서도 Artillery 외에 `socket.io-client`를 직접 사용하는 [방식](https://socket.io/docs/v4/load-testing/)을 안내하고 있었기 때문에, 방향 자체는 틀리지 않았다고 생각했습니다.

이런 방향으로 구현한다면, 모든 소켓이 같은 프로세스 안에 있으니, 유저 A가 보낸 `move`에 대해 유저 B, C, D가 `user_moved`를 수신했는지 자유롭게 집계할 수 있고, 2-Phase 흐름(`init` 완료 → 안정화 대기 → `move` 시작)도 `Promise.all`과 `sleep`으로 간단하게 제어할 수 있습니다. 물론 RTT 계산이나 수신율 집계 같은 통계 로직은 직접 작성해야 하지만, 측정할 수 없는 것보다는 괜찮은 선택이라고 생각했고, AI를 잘 활용하면 구현에는 어렵지 않아보였습니다.

### 테스트 코드

앞서 테스트 시나리오를 구성한 대로 **2-Phase**를 생각해서 구현했습니다. 모든 유저의 `connect` + `init`을 먼저 완료한 뒤, 모든 사용자가 `init_ok`를 받았다면, 일정 대기 시간 뒤에 `move`를 시작하는 방식입니다. 이렇게 분리하면 `move` 구간만 깨끗하게 측정할 수 있게 됩니다.

```javascript
// 단일 Node.js 프로세스 안에서 N개의 소켓 연결을 동시에 관리
const sockets = [];

// Phase 1: 전원 connect + init
const initPromises = tokens.map((token, i) =>
  (async () => {
    if (STAGGER_MS > 0) await sleep(i * STAGGER_MS);
    return connectAndInit(token);
  })(),
);
const results = await Promise.all(initPromises);
const readySockets = results.filter((r) => r.ok).map((r) => r.socket);

// Settle: init I/O가 완전히 끝나도록 대기
await sleep(SETTLE_MS);

// Phase 2: 일제히 move 시작
await Promise.all(readySockets.map((socket) => runMoveLoop(socket)));
```

각 유저의 move 루프에서는 emit 시점과 서버의 `user_moved` broadcast 수신 시점의 차이로 **move (RTT)**도 측정합니다.

```javascript
function runMoveLoop(socket) {
  return new Promise(async (resolve) => {
    let pendingMoveTime = 0;

    // broadcast 수신 시 RTT 측정
    socket.on("user_moved", () => {
      if (pendingMoveTime > 0) {
        stats.moveLatencies.push(Date.now() - pendingMoveTime);
        pendingMoveTime = 0;
      }
    });

    for (let i = 0; i < MOVE_COUNT; i++) {
      const dir = DIRECTIONS[Math.floor(Math.random() * 4)];
      pendingMoveTime = Date.now();
      socket.emit("move", { direction: dir, moveType: "running" });
      stats.totalMovesSent++;
      await sleep(THINK_MS);
    }

    socket.disconnect();
    resolve();
  });
}
```

테스트가 끝나면 connect 지연, init 왕복 지연, move 왕복 지연의 p50/p95/p99 백분위수를 출력합니다.

### 모니터링

CPU 사용량을 측정하는 방법으로는 `Grafana`을 사용하는 것과 `docker stats`를 사용하는 방법이 있었습니다.

#### docker stats

`docker stats` 명령어는 실행 중인 도커 컨테이너의 CPU, 메모리, 네트워크 I/O, 디스크 I/O 사용량을 읽어서, 순간의 스냅샷을 찍어서 보여줍니다.

```bash
seophohoho@poposafari:~/projects/server$ docker stats poposerver_socket
CONTAINER ID   NAME                CPU %     MEM USAGE / LIMIT   MEM %     NET I/O          BLOCK I/O        PIDS
de0d7c3ce4ed   poposerver_socket   2.60%     45.89MiB / 512MiB   8.96%     186MB / 1.01GB   303kB / 1.86MB   12
```

하지만 명령어를 실행한 그 순간의 CPU만 보여주고 이전 수치는 사라지기 때문에, 모니터링으로는 적합해보이지 않았습니다.

#### Grafana

`docker stats`는 순간 스냅샷만 보여주고 이전 기록이 남지 않는다는 단점이 있었습니다. 부하 테스트에서는 테스트 구간 전체의 CPU 사용량을 그래프로 확인해야 하는데, `docker stats`로는 이게 불가능합니다. 반면에 `Grafana`는 데이터를 대시보드로 시각화해주는 도구이기 때문에, 테스트 구간의 CPU 사용량 변화를 그래프로 확인할 수 있습니다.

하지만 컨테이너의 CPU 사용량 같은 메트릭을 직접 수집하지는 않기 때문에, `cAdvisor`라는 툴을 사용하고자 합니다. Google이 만들었고, 실행 중인 컨테이너의 CPU, 메모리, 네트워크, 디스크 I/O 같은 리소스 사용량을 자동으로 수집해줍니다. Docker 데몬의 cgroup 정보를 직접 읽기 때문에, 별도의 설정 없이 모든 컨테이너의 메트릭을 수집할 수 있습니다.

또 하나 생각해야 할 점은 `cAdvisor`는 수집만 해주고 수집한 데이터를 저장해주지는 않는다는 점입니다. `cAdvisor`의 `/metrics` 접속하면 당시 시점의 메트릭을 볼 수 있지만, 과거 데이터를 조회하거나 쿼리를 날리는 것은 불가능합니다. 그래서 `Prometheus`라는 데이터베이스를 사용해야 합니다. `Prometheus`는 `cAdvisor`의 `/metrics` 엔드포인트를 주기적으로 스크래핑(polling)해서 메트릭을 저장하는데, 저장된 데이터는 PromQL이라는 쿼리 언어로 조회할 수 있고, `Grafana`가 이 `Prometheus`를 데이터 소스로 연결해서 대시보드를 그려줍니다.

결국 CPU 사용량 모니터링은 **cAdvisor(수집) → Prometheus(저장) → Grafana(시각화)** 조합을 사용하기로 하였습니다.

#### docker stats와 Grafana의 수치가 다른 이유

CPU 사용량이 `Grafana`에 원할하게 잘 뜨는지 확인하기 위해서, `docker stats 소켓 서버`와 `Grafana`를 모두 띄운 채로 50명 동접자의 부하 테스트를 걸어보고, 두 CPU의 피크를 확인해보았습니다.
`docker stats`에서는 최대 194.06%까지 올랐고, `Grafana`에서는 최대 21.1%까지 올랐다는 결과가 나왔습니다. 왜 수치가 다르게 표기가 된 것일까요? 그리고 어떤 것이 정확할까요?

이유는 계산하는 시간 구간이 각각 달랐기 때문이었습니다.

[docker_stats_percentage](https://stackoverflow.com/questions/47401648/docker-stats-with-cpu-percentage-more-than-100), [docker stats가 1초마다 실행된다는 것. "The table refreshes roughly once per second"](https://www.dash0.com/guides/docker-stats) 이 블로그와 스택오버플로우를 읽어보면, docker stats는 1초 간격으로

```
(현재 cgroup CPU 사용량 - 직전 cgroup CPU 사용량) / (현재 시스템 시간 - 직전 시스템 시간) × 100
```

이 공식을 따른다고 합니다. 즉, `docker stats`에서 표시 된 cpu 사용량은 1초 구간의 평균이었습니다.

Grafana에서 사용하던 CPU 사용량 패널의 쿼리를 살펴보았습니다.

```
sum(rate(container_cpu_usage_seconds_total{name="poposerver_socket"}[5m])) * 100
```

이 쿼리는 `rate(...[5m])`로 **5분 구간의 초당 평균 CPU 사용률**을 구하고, `sum()`으로 모든 코어의 값을 합산한 뒤, `× 100`으로 퍼센트로 변환합니다.

제 부하 테스트의 move 구간은 약 30초(300보 × 96ms)밖에 되지 않습니다. 30초 동안 CPU를 많이 썼더라도, `rate()`가 5분(300초) 구간으로 평균을 내기 때문에 나머지 4분 30초의 idle 시간이 섞여서 피크가 뭉개지게 됩니다.

```
만약에 테스트 30초 동안 최대 CPU 200% 사용하고 있었다면?

docker stats → ~200% (1초 간격 스냅샷이라 실제 피크에 가까움)
Grafana [5m]  → ~20%  ((200% × 30초 + 0% × 270초) / 300초 ≈ 20%, 실제 피크보다 뭉개짐)
```

실제로 `docker stats`에서 194.06%, `Grafana`에서 21.1%가 나온 것도 이렇게 피크가 뭉개진 것으로 설명이 됩니다. 둘 다 틀린 값은 아니지만, 보는 시간 범위가 다른 것이었습니다.

부하 테스트처럼 짧은 구간의 피크를 정확히 관측하려면, `rate`의 구간을 테스트 지속 시간에 맞게 줄이면 됩니다.

```
sum(rate(container_cpu_usage_seconds_total{name="poposerver_socket"}[30s])) * 100
```

`[5m]`을 `[30s]`로 변경한 뒤 같은 테스트를 다시 측정해보니, `docker stats`에서는 196%, `Grafana`에서는 126%가 나왔습니다. 그래도 차이는 있었지만, `[5m]`일 때를 비교하면 훨씬 실제 피크에 가까워진 것을 확인할 수 있었습니다. 결국 CPU 수치에 "정답"이 있는 게 아니라, 어떤 시간 구간으로 평균을 내느냐에 따라 기준이 달라지는 것이기 때문에, 중요한 건 테스트 간에 동일한 기준을 일관되게 사용하는 것입니다. 이제부터 모든 테스트 결과는 이 `[30s]` 쿼리 기준으로 측정하는 것이니, 이 점 참고하시면서 읽어주시면 됩니다.

### CPU 사용율

| 지표                | 10명  | 50명 | 100명 | 150명 | 200명 |
| ------------------- | ----- | ---- | ----- | ----- | ----- |
| **서버 CPU 사용율** | 38.3% | 121% | 137%  | 151%  | 118%  |

`Node.js`는 메인 스레드가 1개입니다. 그렇기 때문에, JavaScript 코드가 사용할 수 있는 CPU는 최대 100%(코어 1개)라고 생각하시면 됩니다. 하지만 테스트 결과를 보시면 50명부터 100%를 넘어버리는 상황이 생겼습니다. 어떻게 싱글 스레드인 `Node.js`가 100%를 넘길 수 있는 걸까요?

`Node.js`는 JavaScript 실행은 메인 스레드 1개에서 하지만, 그게 전부가 아닙니다. 내부적으로 `libuv` 스레드 풀(디폴트 값은 4개라고 합니다^^)이 파일 I/O나 DNS 조회 같은 작업을 처리하고, V8 엔진의 GC(Garbage Collection)도 별도 스레드에서 동작합니다. `cAdvisor`가 측정하는 CPU 사용량은 컨테이너 안에서 돌아가는 **모든 스레드의 CPU 시간을 합산**한 값이기 때문에, 메인 스레드가 100%를 쓰면서 동시에 libuv 스레드 풀이나 GC 스레드, 커널의 네트워크 I/O 처리가 추가로 CPU를 사용하면 합계가 100%를 넘기게 됩니다.

즉, CPU 121%라는 수치는 메인 스레드가 코어 1개를 꽉 채우고 있고, 나머지 21%는 GC나 커널의 네트워크 I/O 처리가 추가로 다른 코어를 사용하고 있음을 보여준다는 소리이기 때문에 **메인 스레드의 이벤트 루프가 포화 상태**라는 뜻이기도 합니다.

그런데 한 가지 이상한 점이 있습니다. 10명 → 50명 → 100명 → 150명까지는 CPU가 38% → 121% → 137% → 151%로 계속 올라가는데, 200명에서는 오히려 118%로 떨어졌습니다. 동접자가 늘었는데 CPU가 줄어든다는 건 이상했습니다.

### Broadcast 수신율

앞서 설명드렸지만, 제 서버에서는 유저로부터 `move` 이벤트를 수신하면, 같은 방의 (본인을 제외한) 모든 유저에게 `user_moved`를 개별적으로 `emit` 합니다. N명이 같은 방에 있을 경우, 1회 move 당 (N-1)개의 broadcast가 발생하기 때문에 기대 수신량은

```bash
기대 수신량 = 총 move 전송 수 x (N-1)
```

이런 공식을 세울 수 있습니다.

하지만, 테스트 결과를 확인해보면,

| 동접  | 총 move 전송 | 기대 수신량 | 실제 수신 | **수신율** |
| ----- | ------------ | ----------- | --------- | ---------- |
| 10명  | 3,000        | 27,000      | 26,739    | **99.0%**  |
| 50명  | 15,000       | 735,000     | 305,961   | **41.6%**  |

| 200명 | 60,000       | 11,940,000  | 228,253   | **1.9%**   |

동접자가 많아질수록, 수신율은 대폭 떨어진다는 것을 확인할 수 있었습니다.

### Broadcast RTT

유저 A가 move 이벤트를 전송하면, 같은 방의 다른 유저 B가 user_moved를 수신 받을 때의 RTT를 말하는 것입니다.

| 동접  | p50  | p95  | p99   | min | max   |
| ----- | ---- | ---- | ----- | --- | ----- |
| 10명  | 72ms | 96ms | 100ms | 0ms | 106ms |
| 50명  | 50ms | 94ms | 101ms | 0ms | 108ms |
| 100명 | 49ms | 94ms | 99ms  | 0ms | 111ms |
| 150명 | 50ms | 93ms | 98ms  | 0ms | 145ms |
| 200명 | 51ms | 93ms | 98ms  | 0ms | 108ms |

정상적으로 수신된 broadcast에 한해서는 RTT는 동접자 수와 무관하게 안정적인 것을 확인할 수 있었습니다.

### 테스트 결과에 대한 판단

Broadcast RTT는 동접 수와 무관하게 p50 ~50ms, p95 ~94ms로 안정적인 상태를 유지하고 있었습니다.

하지만, 클라이언트 측으로 전달되지 못하는 이벤트가 **너무** 많이 있었습니다. 10명일 때는 99%가 전달되었지만, 50명부터 수신율이 41.6%로 급락하고, 100명에서는 13.9%, 200명에서는 1.9%까지 떨어졌습니다. 게임에서 다른 플레이어의 움직임이 100번 중 2번만 보인다면, 사실상 실시간 기능이 동작하지 않는 것과 같습니다.

원인은 이벤트 루프가 포화 상태(CPU 121%)가 되었기 때문에, broadcast를 제때 전달하지 못하는 것이 아닐까? 만약 제 생각이 맞다면, 무엇이 CPU를 많이 쓰게 만들고 있었을까요?

## 무엇이 CPU를 많이 쓰고 있을까?

### CPU 프로파일링

정확하게 제 로직의 어느 부분이 CPU를 많이 쓰고 있는지 확인하기 위해서, CPU 프로파일링을 해보았습니다.

CPU 프로파일링이란, 프로그램이 실행되는 동안 CPU가 어떤 함수를 실행 중인지 통계적으로 확인할 수 있도록 하는 방법입니다.

Node.js는 V8 엔진의 내장 프로파일러를 제공하고 있었습니다. `--cpu-prof` 옵션을 붙여서 서버를 실행하면, **프로세스가 종료될 때** `.cpuprofile` 파일이 자동으로 생성됩니다.

```bash
# 기본적인 실행
node dist/main.js

# CPU 프로파일링 활성화
# `--cpu-prof`: V8의 샘플링 프로파일러를 활성화합니다.
# `--cpu-prof-dir`: `.cpuprofile` 파일이 저장될 디렉터리를 지정합니다.
node --cpu-prof --cpu-prof-dir=./ dist/main.js
```

서버를 프로파일링 모드로 실행한 상태에서 부하 테스트를 돌리고, 테스트가 끝나면 서버 프로세스를 종료합니다. 그러면 `CPU.{날짜}.{시간}.{pid}.0.001.cpuprofile` 형식의 파일이 생성됩니다.

저의 경우, 서버가 Docker 컨테이너 안에서 돌아가고 있었기 때문에, 컨테이너의 `CMD`를 `node --cpu-prof`로 변경하고, 컨테이너를 `docker stop`으로 정상 종료한 뒤, `docker cp`로 `.cpuprofile` 파일을 꺼내는 방식을 사용했습니다.

#### writev가 뭘까?

`--cpu-prof` 프로파일러는 **JavaScript 레벨의 함수만** 추적할 수 있기 때문에, JS 영역 바깥에서 실행되는 네이티브 코드나 시스템 콜은 경로를 알 수 없다고 합니다. 그러면 혹시 `writev`는 시스템 콜이 아닐까? 혹시나 해서, `node.js cpuprofile writev`라고 구글링을 해보니, 이것이 `writev`라는 시스템 콜일 수도 있다는 가능성을 볼 수 있었습니다.

#### perf로 OS 레벨에서의 콜 스택을 확인해보자

정말로 `writev`가 시스템 콜인지를 검증하기 위해서, `perf`라는 툴을 사용하였습니다. `perf`는 리눅스의 OS 커널 수준에서 시스템 콜을 추적할 수 있는 툴이고, 특정 시스템 콜이 호출되는 시점에 전체 콜 스택을 기록할 수 있습니다.

#### writev가 호출되기까지의 흐름

`perf`의 콜 스택을 아래에서 위로 읽어보면, 제 코드에서 `writev` 시스템 콜까지 어떤 경로로 도달하는지 알 수 있습니다.

```
[내 서버 코드]   io.to(roomId).emit('user_moved', ...)
       ↓
[Engine.IO]      sendPacket()  — Socket.IO 패킷을 Engine.IO 프레임으로 감쌈
       ↓
[ws 라이브러리]   sendFrame()  — WebSocket 프레임으로 인코딩
       ↓
[Node.js Stream] Writable.uncork() → clearBuffer() → Socket._writev()
       ↓
[Node.js C++]    StreamBase::Writev() → LibuvStreamWrap::DoTryWrite()
       ↓
[libc]           writev()
```

결국, 제가 작성한 `io.to(roomId).emit(...)` 한 줄이 내부적으로는 **방에 있는 유저 수만큼 `writev` 시스템 콜을 호출**하고 있었던 것입니다.

#### 그래서 writev 시스템 콜이 뭐냐?

[이 문서](https://www.ibm.com/docs/en/i/7.6.0?topic=ssw_ibm_i_76/apis/writev.html)에 따르면, `writev`란, 파일이나 소켓 디스크립터에 데이터를 쓰는 데 사용된다고 합니다. 다른 사용자에게 브로드캐스트를 날릴 때, 이 시스템 콜이 사용되고 있었습니다.

### 내 프로젝트에서는 무엇이 문제였을까?

다시 제 로직을 살펴보면, 유저 A가 `move` 이벤트를 보내면, 서버가 **즉시** 같은 방의 모든 유저에게 `user_moved`를 브로드캐스트했습니다.

```typescript
// 기존 코드: move 이벤트를 받자마자 즉시 브로드캐스트
socket.on("move", async ({ direction, moveType }) => {
  // ... 좌표 계산, Redis 저장 ...
  this.io.to(roomId).emit("user_moved", { userId, x, y, direction, moveType });
});
```

`io.to(roomId).emit()`은 방에 있는 **각 소켓마다 개별적으로** 데이터를 직렬화하고 `writev`를 호출합니다. N명이 같은 방에 있을 때, 1회의 `emit`이 N번의 `writev`를 발생시킵니다.

그런데 N명이 **동시에** 이동하고 있으므로, 96ms(ride 이동 간격) 동안 N번의 `move` 이벤트가 들어옵니다. 각 `move`마다 N번의 `writev`가 발생하니, **96ms마다 N × N번의 `writev`가 호출**되는 것입니다.

```
100명 기준:
96ms마다 100회 move × 100번 writev = 10,000번의 writev / 96ms
→ 초당 약 104,000번의 writev 시스템 콜
```

`writev` 한 번은 괜찮지만, 초당 10만 번이 넘어가면 문제가 됩니다. 시스템 콜은 **유저 공간 → 커널 공간** 전환(context switch)을 수반하고, 커널은 TCP 소켓의 send 버퍼에 데이터를 복사하고, 패킷을 구성하고, 네트워크 스택을 통해 전송해야 합니다. 이 과정이 초당 10만 번 반복되면, CPU 시간의 대부분이 `writev`에 소비되는 것입니다.

CPU 프로파일링에서 `writev`가 **74.2%**를 차지했다는 결과가 이유가 있었습니다. 제 비즈니스 로직(좌표 계산, Redis 조회)이 아니라, **소켓에 데이터를 쓰기**가 CPU를 잡아먹고 있었던 것이었습니다.

#### Node.js 이벤트 루프와의 관계

Node.js의 이벤트 루프는 여러 **단계(phase)**를 순환하며 실행됩니다.

```
   ┌───────────────────────────┐
┌─>│         timers            │ ← setTimeout, setInterval 콜백 실행
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │     pending callbacks     │ ← 시스템 콜의 에러 콜백 등
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │       idle, prepare       │ ← 내부 용도
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │          poll              │ ← I/O 이벤트 수신 및 콜백 실행
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │          check             │ ← setImmediate 콜백 실행
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │     close callbacks       │ ← socket.on('close') 등
│  └───────────────────────────┘
```

현재 제일 중요하게 봐야 할 단계는 **poll** 입니다. 소켓으로부터 `move` 이벤트가 도착하면, poll 단계에서 해당 콜백이 실행됩니다. 그런데 이 콜백 안에서 `io.to(roomId).emit()`을 호출하면, N명에게 보내기 위한 `writev`가 **동기적으로** 실행됩니다. 즉, poll 단계에서 `move` 콜백 하나를 처리하는 데 N번의 `writev`가 끝날 때까지 기다려야 합니다.

그 사이에도 다른 유저들의 `move` 이벤트는 계속 도착하고 있습니다. 이 이벤트들은 poll 큐에 쌓이지만, 현재 콜백의 `writev` N번이 끝나야 다음 콜백을 처리할 수 있습니다. 결국 poll 큐에 이벤트가 쌓이는 속도가 처리 속도를 초과하면, **이벤트 루프가 포화 상태**에 빠지게 됩니다.

이것이 앞서 관측한 현상들의 원인입니다.

- **CPU 100% 초과**: 메인 스레드가 `writev`로 코어 1개를 꽉 채우고, OS 커널의 네트워크 I/O 처리가 다른 코어를 추가로 사용
- **broadcast 수신율 급락**: poll 큐가 포화되어 새로운 이벤트 처리가 지연되고, 소켓 send 버퍼가 가득 차면서 Socket.IO가 내부적으로 이벤트를 드롭
- **200명에서 CPU가 오히려 하락**: 이벤트 루프가 이벤트를 꺼내는 것조차 느려져서, 실제 처리량 자체가 줄어듦

정리하면, 문제의 본질은 **"move 이벤트 1건마다 즉시 N번의 writev를 호출하는 구조"**였습니다. 이벤트 수가 O(N)이고, 건당 `writev`가 O(N)이니, 전체 `writev` 호출 횟수는 **O(N²)**로 증가합니다.

### 이걸 어떻게 해결할까?

O(N²)으로 폭증하는 `writev` 호출을 줄이는 방법을 고민했고, 두 가지 접근법을 검토했습니다.

#### AOI 기법

AOI(Area of Interest)는 맵을 논리적인 그리드(영역)로 나누고, 유저가 위치한 영역과 그 주변 영역에 있는 유저에게만 이벤트를 전달하는 기법입니다. MMORPG에서 널리 사용되는 방식으로, 맵이 넓고 유저가 여러 곳에 분산되어 있을 때 효과적입니다. 예를 들어, 맵을 9개 구역으로 나누면 유저 A의 움직임은 A가 속한 구역과 인접한 구역의 유저에게만 전달되므로, 브로드캐스트 대상이 N명에서 N/9명 수준으로 줄어듭니다.

하지만 제 프로젝트의 맵들은 크기 자체가 그렇게 크지 않았고, 맵 전체의 약 70%가 유저가 이동할 수 없는 타일(나무, 벽, 물 등)로 채워져 있었습니다. 실제로 유저가 돌아다닐 수 있는 영역은 맵의 30% 정도에 불과했기 때문에, AOI로 영역을 나눠봤자 대부분의 유저가 결국 같은 영역에 몰리게 될 가능성이 높았습니다. 그러면 AOI를 적용해도 브로드캐스트 대상 수는 크게 줄지 않으므로, 구현 복잡도 대비 효과가 미미할 것이라고 판단했습니다.

#### Tick

게임 서버에서 많이 사용하는 또 다른 방법이 있었습니다. 바로 **Tick** 방식입니다.

Tick이란, 일정한 시간 간격(Tick Rate)마다 서버가 게임 상태를 한꺼번에 처리하고 클라이언트에 전달하는 방식입니다. 실제 많은 멀티플레이어 게임 서버가 이 방식을 사용하고 있다고 합니다.

기존 방식과 Tick 방식의 차이를 비교해보면 이렇습니다.

**기존 방식: 이벤트 즉시 브로드캐스트**

```
시간축 →
유저A move → 즉시 broadcast(N번 writev)
유저B move → 즉시 broadcast(N번 writev)
유저C move → 즉시 broadcast(N번 writev)
...
96ms 동안 N명이 move → N × N번 writev
```

**Tick 방식: 일정 주기로 모아서 브로드캐스트**

```
시간축 →
유저A move → 버퍼에 저장
유저B move → 버퍼에 저장
유저C move → 버퍼에 저장
...
[Tick!] → 버퍼에 쌓인 이동 정보를 하나의 이벤트로 묶어서 broadcast(N번 writev)
```

**N번의 개별 broadcast를 1번의 묶음 broadcast로 합치는 것**입니다. N명의 이동 정보를 한 곳에 담아 한 번만 브로드캐스트하면, Tick 1회당 `writev` 호출은

```
기존 방식: 96ms당 N × N번 writev  → O(N²)
Tick 방식: 50ms당 N번 writev      → O(N)
```

**O(N²)이 O(N)으로 바뀝니다.** 이것이 Tick의 핵심입니다.

제 구현에서는 Tick Rate를 **50ms(초당 20tick)**로 설정했습니다. 이 값은 유저가 가장 빠르게 이동하는 ride 타입의 96ms보다 짧기 때문에, 유저의 이동을 빠짐없이 수집할 수 있습니다. 동시에, 50ms 간격이면 사람이 체감하기 어려운 수준의 지연이기 때문에 게임 경험에도 영향이 없습니다.

구현은 크게 두 부분으로 나뉩니다.

**1. move 이벤트 핸들러: 즉시 브로드캐스트 대신 버퍼에 저장**

```typescript
socket.on("move", async ({ direction, moveType }) => {
  // ... 좌표 계산, Redis 저장 (기존과 동일) ...

  // 변경: 즉시 broadcast 하지 않고, 버퍼에 저장
  if (!this.moveBuffer.has(roomId)) this.moveBuffer.set(roomId, new Map());
  this.moveBuffer.get(roomId)!.set(userId, {
    x: curX,
    y: curY,
    direction,
    moveType,
    lastMoveTime: now,
  });
});
```

`moveBuffer`는 `Map<roomId, Map<userId, MoveBufferEntry>>` 구조입니다. 같은 유저가 Tick 사이에 여러 번 이동하면, 마지막 위치만 덮어쓰기 때문에 불필요한 중간 상태가 자동으로 제거됩니다.

**2. Tick 루프: 일정 주기로 버퍼를 비우며 브로드캐스트**

```typescript
private startTickLoop(): void {
  this.tickInterval = setInterval(() => {
    this.moveBuffer.forEach((usersMap, roomId) => {
      if (usersMap.size === 0) return;
      const updates = Array.from(usersMap.entries()).map(([userId, entry]) => ({
        userId,
        ...entry,
      }));
      this.io.to(roomId).emit("users_moved", { updates });
      usersMap.clear();
    });
  }, TICK_RATE_MS); // 50ms
}
```

`setInterval`로 50ms마다 버퍼를 순회하며, 각 방에 쌓인 이동 정보를 `updates` 배열로 묶어서 **`users_moved`라는 단일 이벤트**로 브로드캐스트하고, 버퍼를 비웁니다.

#### Tick 적용 전/후 비교

Tick을 적용한 뒤, 동일한 테스트 시나리오(N=10~200, THINK_MS=96, MOVE_COUNT=300)로 다시 부하 테스트를 돌려보았습니다.

**CPU 사용율 비교**

| ----- | ----------------------- | ----------------- | ------ |
| 10명  | 38.3%                   | 27.3%             | -28.7% |
| 50명  | 121%                    | 54.7%             | -54.8% |
| 100명 | 137%                    | 85.4%             | -37.7% |
| 150명 | 151%                    | 104%              | -31.1% |
| 200명 | 118%                    | 110%              | -6.8%  |

**Broadcast 수신율은 비교할 수 있을까?**

Tick 적용 전에는 move 1건에 대해 `user_moved` 1건이 1:1로 대응했기 때문에, 기대 수신량과 실제 수신량을 비교해서 수신율을 명확하게 계산할 수 있었습니다.

하지만 Tick 적용 후에는 여러 move가 하나의 tick 프레임으로 합쳐지고, 같은 유저의 중복 이동은 마지막 위치만 남기 때문에, 기존과 같은 기준의 "기대 수신량"을 산출할 수 없게 되었습니다. tick 프레임의 순번(`tickSeq`) 기반으로 수신율을 측정할 수는 있지만, 소켓별 연결/해제 시점의 차이로 인해 매 실행마다 수치가 달라지는 한계가 있었습니다.

결국 Tick 적용 전후의 수신율을 동일 기준으로 직접 비교하는 것은 어렵다고 판단했습니다. 다만, 핵심은 **CPU 사용율이 100% 이하로 내려왔다는 것**입니다. 앞서 확인했듯이 broadcast 유실의 원인은 이벤트 루프 포화였고, CPU가 포화 상태에서 벗어났다면 이벤트 전달도 정상화되었다고 볼 수 있습니다.

## 마무리

처음에 세웠던 세 가지 목표를 하나씩 점검해보겠습니다.

**1. 서버 한계 파악**

기존 구현에서는 동접 10명일 때 CPU 38.3%로 여유가 있었지만, 50명부터 121%로 이벤트 루프가 포화 상태에 진입했습니다. broadcast 수신율도 50명에서 41.6%로 급락했기 때문에, 기존 구조에서는 **같은 맵에 약 10명**이 사실상 쾌적한 플레이의 한계였습니다.

**2. 병목 지점 식별**

CPU 프로파일링과 `perf`를 통해, CPU의 74.2%가 `writev` 시스템 콜에 소비되고 있다는 것을 확인했습니다. move 이벤트 1건마다 N명에게 즉시 broadcast하는 구조가 O(N²)의 `writev` 호출을 만들어내고 있었고, 이것이 이벤트 루프 포화와 broadcast 유실의 원인이었습니다.

**3. 개선 및 검증**

Tick 기반 브로드캐스트를 적용하여, N번의 개별 broadcast를 50ms마다 1번의 묶음 broadcast로 합쳤습니다. 그 결과 `writev` 호출이 O(N²)에서 O(N)으로 줄었고, 동접 100명 기준으로 CPU가 137% → 85.4%로 내려왔습니다. 100명까지는 CPU가 100% 이하를 유지하기 때문에, 기존 **약 10명에서 약 100명**까지 쾌적한 동접 가능 인원을 늘릴 수 있었습니다.
