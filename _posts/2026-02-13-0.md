## 들어가며

poposafari는 `phaser3`라는 게임 엔진을 사용하여 개발하고 있는 웹 게임입니다. 그렇기 때문에, 게임에 필요한 여러 에셋(이미지, 사운드, 스프라이트 시트)들을 사이트에 접속 시에 로드(load) 해야 할 필요가 있었는데요. 에셋을 새롭게 추가하면 추가할수록, 로딩되는 시간은 갈수록 길어지게 되었고, 결국 로딩 시간이 로컬 환경임에도 불구하고 27초까지 걸리게 되는 상황까지 오게 되었습니다. 가장 큰 문제는 사용자가 **로딩 UI를 너무 오래 봐야 한다**는 점이었어요. 게임에 들어가기도 전에 20초 넘게 기다리다 보면 이탈하기 쉽고, 사용자 경험 자체가 해쳐진다고 느꼈습니다. 이번 글에서는 이미지 패킹이라는 것을 통해서 웹 브라우저가 받는 에셋 데이터의 로딩 시간을 단축시킬 수 있었던 과정을 공유하고자 합니다.

## 문제의 원인을 파악하는 과정

### Stalled(회색 막대)가 이렇게 길어진 이유는?

Waterfall에서 눈에 먼저 들어온 건 **회색으로 길게 잡힌 Stalled** 구간이었습니다. Stalled가 정확히 뭘 의미하는지 찾아 보니, **"요청을 실제로 전송할 수 있게 되기까지 기다리는 시간"**이라는 걸 알게 됐습니다. 즉, 아직 서버에 요청을 보내지도 못하고 **빈 연결이 나올 때까지 기다리는 시간**이라는 겁니다.

"왜 stalled가 있어야 할까?" **HTTP/1.1** 환경에서는 브라우저가 **도메인당 동시에 최대 6개**의 TCP 연결만 허용한다는 걸 알게 됐습니다. 요청이 22,000개면 6개씩 묶여 순차적으로 처리되니까, 대부분의 요청이 "앞에 처리가 끝날 때까지 기다리는" Stalled 상태로 남는 겁니다.

그런데 여기서 중요한 건, **제가 로컬 환경에서 개발하고 있었기 때문**에 브라우저가 자동으로 **HTTP/1.1**만 사용했다는 점입니다. 로컬 개발 서버는 보통 HTTPS를 쓰지 않고 있기 때문에, [HwanShell 글](https://hwan-shell.tistory.com/389)에서 정리한 것처럼 "HTTPS 통신을 하지 않는 서버 같은 경우에는 강제로 HTTP 1.1을 사용하게 됩니다." 그래서 **동시 요청 처리 제한(도메인당 6개)**이 그대로 걸려 있었고, 22,000개 요청이 6개 창구에만 몰리면서 Stalled가 끝없이 쌓였던 거죠.

### HTTP/1.1과 HTTP/2의 차이

연결 제한과 "왜 6개인가"를 더 이해하려고, HTTP/1.1과 HTTP/2를 비교한 글들을 참고해 정리했습니다.

| 구분 | HTTP/1.1 | HTTP/2 |
|------|----------|--------|
| **연결** | 도메인당 동시 연결 **6~8개** 제한. 그 이상은 Stalled(대기). | **한 연결**에서 여러 요청/응답을 동시에 처리(**멀티플렉싱**). 동시 요청 개수 제한이 사실상 없음. |
| **프로토콜** | **텍스트** 기반 (가독성은 좋지만 파싱·처리 비용 큼). | **바이너리** 프레이밍. 파싱이 빠르고 오류 처리도 단순해짐. |
| **헤더** | 매 요청마다 **같은 헤더를 반복 전송**. 작은 파일일수록 헤더 비중이 커짐. | **HPACK**으로 헤더 압축. 동적 테이블로 반복되는 헤더를 인덱스만 보내서 크기 대폭 감소. |
| **처리 방식** | 한 연결에서 요청을 **순차 처리**. 앞 요청이 지연되면 뒤 요청 전부 대기(**Head-of-Line Blocking**). | 한 연결 안에 여러 **스트림**을 두고, 스트림 단위로 동시에 주고받음. 한 요청이 막혀도 다른 스트림은 진행. |

정리하면, **로컬(localhost)**처럼 HTTPS를 쓰지 않는 환경에서는 HTTP/1.1만 쓰게 되고, 그래서 **동시에 처리할 수 있는 요청이 6개로 제한**된 상태였습니다. HTTP/2를 쓸 수 있는 환경이면 같은 수의 요청이라도 멀티플렉싱과 헤더 압축 덕분에 나아지지만, **요청 개수 자체를 줄이는 것**이 중요하다고 생각이 들었습니다.

### 전송 용량이 49MB인데 왜 76MB 일까?

에셋 폴더는 49MB 정도인데, Network 탭에는 전송 76.2MB, 리소스 97.7MB로 찍혀 있어서 **"어디서 용량이 부풀어 나오지?"**를 알아보았습니다.

HTTP로 파일을 한 번 요청할 때는 **파일 내용만** 주는 것이 아니라, 매 요청마다 **Request Header**와 **Response Header**가 함께 전송됩니다.

각 파일별로 얼만큼 용량이 늘어났는지 확인하려면, 브라우저 콘솔에서 아래 코드를 실행하면 됩니다.

```javascript
function formatBytes(bytes) {
  if (bytes === 0) return '0 B';
  const k = 1024;
  const sizes = ['B', 'KB', 'MB', 'GB'];
  const i = Math.floor(Math.log(bytes) / Math.log(k));
  return parseFloat((bytes / Math.pow(k, i)).toFixed(2)) + ' ' + sizes[i];
}

performance.getEntriesByType('resource').forEach((e, i) => {
  const transferred = formatBytes(e.transferSize);
  const decoded = formatBytes(e.decodedBodySize);
  const shortName = e.name.split('/').pop() || e.name;
  console.log(`${shortName}  →  전송(헤더+본문): ${transferred}  |  본문(압축해제): ${decoded}`);
});
```

예를 들어 `0000.png`는 279 Byte인데 전송 크기는 579 Byte로 늘어난 걸 확인할 수 있습니다.
![용량_늘어남1]({{ site.img_path }}/2026-02-13-0_4.png)
![용량_늘어남2]({{ site.img_path }}/2026-02-13-0_5.png)

파일 하나가 1KB여도 실제로는 헤더까지 합쳐 2KB에 가깝게 오갈 수 있고, **22,000개 × 약 1KB (헤더 오버헤드) ≈ 22MB**가 순수 에셋 49MB 위에 더해져서 전송량이 76MB, 리소스 기준 97MB까지 부풀어 보였던 겁니다. HTTP/2에서는 HPACK으로 헤더를 압축해 이 오버헤드를 크게 줄여준다고 합니다.

## 요청 횟수를 줄여보자: 이미지 패킹 (Texture Packer)

원인을 알아보니 . **요청 횟수 자체를 줄이면** 헤더 오버헤드, 연결 병목을 모두 줄일 수 있다고 생각이 들었습니다. 그래서 **pokemon**에 해당하는 에셋 데이터를 **하나의 커다란 이미지로 패킹**하는 방식을 적용해보기로 하였습니다.

### Texture Packer로 하나의 이미지에 모으기

![texture_packer]({{ site.img_path }}/2026-02-13-0_8.png)

**[Texture Packer](https://www.codeandweb.com/texturepacker)**라는 툴을 사용해서, 수천 개에 달하던 포켓몬 스프라이트 이미지들을 **한 장의 큰 이미지(아틀라스)**로 합쳤습니다. 개별 파일(`0000.png`, `0001.png`, …)을 그대로 여러 번 요청하는 대신, **front / icon / overworld** 등 타입별로 하나씩의 시트 이미지와, 각 프레임의 위치·크기 데이터가 들어 있는 JSON을 추가하였습니다.

- 개별 파일 수천 개 → **아틀라스 이미지 1개 + JSON 1개** (타입별로 반복)
- 이렇게 하면 **요청 1번**으로 여러 개의 스프라이트를 한꺼번에 받을 수 있습니다.

![texture_packer]({{ site.img_path }}/2026-02-13-0_10.png)

### 클라이언트에서 loadMultiatlas로 한 번에 로드

기존에는 포켓몬 ID마다 `loadImage`, `loadAtlas`를 반복 호출하고 있었습니다.
```typescript
// 22,000번 반복되는 죽음의 루프
pokemonList.forEach(id => {
    this.load.image(`pokemon_${id}`, `assets/${id}.png`);
});
```

패킹 후에는 **`load.multiatlas`**(또는 `loadMultiatlas`) 한 번으로 해당 아틀라스 전체를 등록할 수 있습니다.
```typescript
// 단 한 번의 호출로 해결 (Multiatlas 지원)
this.load.multiatlas('pokemons', 'assets/packed/pokemon_atlas.json', 'assets/packed');
```

그래서 pokemon 에셋을 **Texture Packer로 하나의 커다란 이미지에 패킹**하고, **loadMultiatlas**로 불러오도록 바꿈으로써 요청 횟수 자체를 크게 줄일 수 있었고, 그 결과 로딩 시간과 전송량을 함께 줄일 수 있었습니다.

![after_결과]({{ site.img_path }}/2026-02-13-0_9.png)

> 요청 수 : 22,117개 -> 629개  
> 전송 용량 : 76.2 MB (실제 리소스 : 97.7 MB) -> > 48.7 MB (실제 리소스 : 58.4 MB)  
> 로딩 완료 시간 : 27.10초 -> 1.93초  
{: .callout .info }

패킹 작업을 통해서 로딩 완료 시간이 27초에서 2초대로 줄었고, 사용자가 로딩 UI를 오래 바라보지 않아도 되게 되었습니다. 게임에 들어가기 전 불필요한 대기 시간이 크게 줄어들어 **사용자 경험**이 눈에 띄게 나아졌습니다.
