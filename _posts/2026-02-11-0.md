## 들어가며

poposafari 프로젝트는 서버 쪽을 `Node.js`로 개발하고 있습니다. 로컬 회원가입 로직을 검토하던 중에 문득 이런 생각이 들었습니다.

> "같은 아이디(username)으로 두 사람이 동시에 가입 버튼을 누르면 어떻게 될까?
{: .callout .question}

당연히 중복 체크 로직이 있었기 때문에, 한 명만 성공하고 나머지는 409 Conflict를 받지 않을까? 싶었지만, 확신이 서지는 않았습니다. 그래서 직접 테스트하기로 했고, 그 과정에 만난 `Race Condition`과 해결 방법을 정리해 보았습니다.

## 테스트를 해보자

제가 작성한 회원가입 로직은 `check-then-act` 패턴을 사용하고 있습니다. 먼저 "이미 있는 유저인가?"를 확인(`check`)하고, 만약 없다면, 회원가입(`Act`)하는 흐름이죠.

```typescript
async registerLocal(req: AuthLocalReq): Promise<TokenPair> {
  const { username, password } = req;

  // 이미 존재하는 username인가? 체크
  const existingAuth = await this.authRepository.findByProviderAndProviderId(
    UserAuthProvider.LOCAL,
    username,
  );

  // 이미 존재한다면 409(CONFLICT) 에러르 던짐
  if (existingAuth) {
    throw new AppError(
      AppErrorMessage.USER_ALREADY_EXISTS,
      409,
      AppErrorCode.CONFLICT
    );
  }

  //비밀번호 암호화
  const hashedPassword = await bcrypt.hash(password, this.SALT_ROUNDS);
  const queryRunner = this.dataSource.createQueryRunner();
  await queryRunner.connect();
  await queryRunner.startTransaction();

  try {
    //회원가입 수행
    const auth = await this.authRepository.create(
      UserAuthProvider.LOCAL,
      username,
      hashedPassword,
    );

    const tokenPair = await this.generateAndStoreTokens(auth.id);
    await queryRunner.commitTransaction();

    return {/*...*/};
  } catch (error) {
    await queryRunner.rollbackTransaction();
    throw error;
  } finally {
    await queryRunner.release();
  }
}
```

순차적으로만 요청을 들어온다면, 크게 문제는 없어 보였습니다. 그래서 **동시에 요청**이 몰렸을 때를 가정하고 테스트를 설계해보았습니다.

### 테스트 툴 선정

**동시에 요청**이 몰리는 상황을 만들기 위해서는 먼저 테스트 툴을 선정해야 했습니다. 구글링 해보니깐, `k6`, `Promise.all`, `Promise.allSettled` 등등 여러 가지가 있었습니다.

`k6`는 본격적인 부하 테스트를 할 수 있는 도구이기 때문에, 동시 접속자 수를 늘려가며 다양한 시나리오를 테스트해 볼 수 있습니다. 다만 이번에 제가 보고 싶었던 건 단 하나, **\"동시에 요청을 보냈을 때 내가 작성한 로직이 의도한 대로 동작하는가\"** 뿐이었기 때문에, k6까지 도입하는 건 조금 과하다고 느꼈습니다.

`Promise.all`나 `Promise.allSettled`는 `Node.js`에서 자체적으로 제공하고, 비동기 작업(Promise)을 배열(Array) 형태로 인자를 받아서, 병렬로 처리해주고, 모든 요청이 완료될 때까지 기다렸다가 결과를 배열로 반환해주는 메소드입니다. 이 방법이 제가 원하는 시나리오를 빠르게 검증해줄 수 있었기 때문에, 가장 적합한 테스트 툴이라고 생각했습니다.

### 동시에 100번 요청 보내기

`Promise.all`을 이용해서 아래처럼 테스트 코드를 작성해보았습니다.

```typescript
const url = '대충 서버 로컬 회원가입 주소';
const payload = {
  username: 'testuser123',
  password: 'password123',
};

//테스트 요청 수 100개로 지정.
const reqs = Array.from({ length: 100 }, () => {
  return axios.post(url, payload).catch((err) => err.response);
});

const res = await Promise.all(reqs);
const summary = res.reduce((acc, res) => {
  const status = res.status || 'What?';
  acc[status] = (acc[status] || 0) + 1;
  return acc;
}, {});

//이쁘게 테이블 형태로 만들어서 결과를 보도록 한다.
console.table(
  Object.entries(summary).map(([status, count]) => ({
    'HTTP Status': status,
    Count: count,
    Result: status === '201' ? 'SUCCESS' : status === '409' ? 'CONFLICT' : 'UNKNOWN',
  })),
);
```

예상했던 결과는 간단했습니다. **1개는 `201`, 나머지 99개는 `409(Conflict)`**가 나온다면 충분히 제 코드가 의도대로 동작하는 거죠.

## 왜 409가 아니라 500일까?

테스트 코드를 실행해보니, 제 예상과는 달랐습니다.

```bash
┌─────────┬─────────────┬───────┬───────────┐
│ (index) │ HTTP Status │ Count │ Result    │
├─────────┼─────────────┼───────┼───────────┤
│ 0       │ '201'       │ 1     │ 'SUCCESS' │
│ 1       │ '500'       │ 99    │ 'ERROR'   │
└─────────┴─────────────┴───────┴───────────┘
```

99개의 요청 결과가 `409(CONFLICT)`가 아니라, `500`을 받고 있었습니다. 서버 측에서 로그를 확인해보니, 원인은 DB(PostgreSQL) 쪽이었습니다.

```bash
POST /api/auth/register/local 500 1730.163 ms - 165
{
    severity: 'ERROR',
    code: '23505',
    detail: 'Key (provider, provider_id)=(local, testuser123) already exists.',
    table: 'auth_identities',
    constraint: 'IDX_b4756e087ec67d0abe2f53792a',
}
```

PostreSQL의 **Unique 제약 조건 위반 에러**였습니다. 다행히 `username`을 유니크 키로 지정해 두었기 때문에 중복 데이터는 막았지만, 사용자는 "서버에 문제가 생겼구나!"는 오해를 주는 `500` 에러 코드를 받게 되는 상황이었습니다.

### 왜 이런 일이 발생했을까?

원인은 **`check-then-act` 패턴의 구조적인 한계**와, 그 패턴이 **Node.js의 비동기 환경 위에서 동작한다**는 점 때문이었습니다.

먼저 `check-then-act` 패턴부터 말씀드리자면, 이름 그대로 **"상태를 확인(check)한 뒤, 그 결과를 믿고 행동(act)하는"** 코드 패턴입니다. 문제는 이 두 단계 사이에 항상 작은 **시간 텀**이 존재한다는 점입니다. 체크(check)할 때는 조건에 부합했지만, 행동(act)를 하려는 찰나에 다른 요청이 먼저 들어와 상태를 바꿔 버릴 수 있습니다.

이번 회원가입 로직에서는 "중복 유저가 있는지 조회"가 check 역할을, "없으니 INSERT"가 act 역할을 했고, 이 사이에 다른 요청들이 끼어들 여지가 충분히 있었습니다.

여기에 Node.js의 실행 방식이 더해지면서 이 여지가 그대로 등장하게 되었습니다. Node.js는 싱글 스레드 기반이지만, DB 조회 같은 I/O 작업은 비동기로 처리하기 때문에, 한 요청이 중복 체크를 위해 DB에 질의해 둔 상태에서 응답을 기다리는 동안에도 다른 요청들이 계속 들어와 같은 조회를 수행할 수 있습니다.

그 결과, 100개의 요청이 **거의 동시에** 중복 체크를 통과하는 상황이 만들어졌습니다. 이 짧은 순간 동안 여러 요청이 같은 상태를 보고 한꺼번에 저장(Act)을 시도하면서, **Race Condition**이 발생하게 된 겁니다.

```
Request 1:  [중복 체크 ✓] -----> [데이터 저장 ✓]
Request 2:  [중복 체크 ✓] -----> [데이터 저장 ✗] (DB 에러!)
Request 3:  [중복 체크 ✓] -----> [데이터 저장 ✗] (DB 에러!)
...
Request 100: [중복 체크 ✓] -----> [데이터 저장 ✗] (DB 에러!)
```

체크 시점에는 아직 아무도 `INSERT`를 하지 않았기 때문에, 모든 요청이 "없다"고 판단하고 저장(Act) 단계로 넘어가게 되었고, 그중 가장 먼저 INSERT를 성공한 1개를 제외한 나머지는 DB Unique 제약에 걸려 에러가 난 것입니다.

## 동시성 문제가 발생하지 않도록 막을 것인가? 대응만 할 것인가?

이걸 어떻게 해결할지 생각해 보면, 크게 두 갈래로 나뉘어 졌습니다.

- **예방(Prevention)**
  Race Condition이 아예 발생하지 않게 만드는 쪽
- **대응(Handling)**
  일어난 에러를 제대로 잡아서 사용자에게 적절한 응답을 주는 쪽

### 만약 예방 한다면?

### 예방법1. 로직 자체를 바꾸자 : `check-then-act`이 아니라 **한 번에 처리**

기존처럼 `SELECT(username이 존재하는지)`로 체크하고, `INSERT(없다면, 회원가입)`한다는 두 단계로 쿼리를 분리하는 것이 아닌 DB에 한 번에 처리하도록 쿼리를 보내는 겁니다.

```sql
INSERT INTO auth_identities (provider, provider_id, password)
VALUES ('local', $username, $hashedPassword)
ON CONFLICT (provider, provider_id) DO NOTHING
RETURNING id;
```

만약 `RETURNING id`가 있다면(해당 row의 id가 리턴된다.), 새롭게 회원가입에 성공했다고 넘어가고,
`RETURNING id`가 없다면, 이미 존재하는 username이라고 판단하고 `409(CONFLICT)`를 사용자에게 전달하는 겁니다.

이 방법을 쓴다면, `check-then-act` 패턴에서 발생하는 `check`와 `act`의 시간 텀을 최소화할 수 있다는 장점이 있습니다.

### 예방법2. 비관적 락 (Persimistic Lock)

동시성 문제를 해결하기 위해서 자주 거론되는 비관적 락을 이용해보는 겁니다.
제 코드 기준이면, 아래처럼 적을 수 있습니다.

```typescript
await queryRunner.startTransaction();

try {
  // username이 이미 존재하는지 확인하면서, 해당 row에 락을 건다
  const existing = await queryRunner.manager.findOne(User, {
    where: { username },
    lock: { mode: 'pessimistic_write' }, // SELECT ... FOR UPDATE
  });

  if (existing) {
    throw new AppError(AppErrorMessage.USER_ALREADY_EXISTS, 409, AppErrorCode.CONFLICT);
  }

  // 없다고 확인됐으니, 이제 안전하게 INSERT
  const user = queryRunner.manager.create(User, { username, password: hashedPassword });
  await queryRunner.manager.save(user);

  await queryRunner.commitTransaction();
} catch (error) {
  await queryRunner.rollbackTransaction();
  throw error;
} finally {
  await queryRunner.release();
}
```

`lock: { mode: 'pessimistic_write' }`는 내부적으로 `SELECT ... FOR UPDATE`를 사용합니다. 이 쿼리가 **SELECT된 row에 대해 row-level lock**을 겁니다. 다른 트랜잭션이 같은 row에 대해 `FOR UPDATE`나 `UPDATE`, `DELETE`를 시도하면, 락을 먼저 잡고 있던 트랜잭션이 COMMIT/ROLLBACK 할 때까지 블로킹 됩니다.

만약 이미 존재하는 username에 대해서는 정상적으로 동작하겠지만, 지금 저의 시나리오는 존재하지 username에 대해서 동시에 회원가입을 요청하는 경우입니다. 그렇기 때문에, `SELECT ... FOR UPDATE`가 조회할 **row 자체가 없어서** 락을 걸 대상이 없고, 결국에는 DB Unique 제약 에러(500)이 발생하게 될 것입니다.

### 예방법3. 낙관적 락 (Optimistic Lock)

낙관적 락은 데이터를 읽을 때는 락을 걸지 않고, 데이터를 업데이트할 때만 이전 데이터와 현재 데이터를 비교하여 충돌 여부를 판단합니다. 하지만, 이 방법을 제 코드에 적용해도 UPDATE 할 만한 row 자체가 없기 때문에, 결국 DB Unique 제약 에러가 나오게 될 것입니다.

만약 낙관적 락을 억지로라도 추가한다면, 아래처럼 작성할 수 있을겁니다.

```typescript
@Entity('auth_identities')
@Index(['provider', 'providerId'], { unique: true })
export class Auth {
  @PrimaryGeneratedColumn({ type: 'bigint' })
  id!: string;

  @VersionColumn() //SET version = version + 1을 수행해준다.
  version: string; //version이라는 것을 추가한다.

  //...
}
```

### 예방법4. 애플리케이션 레벨 락

서버 내에 맵을 두고, 같은 key(username)에 대해서는 한 번에 하나의 회원가입 로직을 수행하게 만드는 겁니다.

```typescript
const locks = new Map<string,Promise<void>>();

async function withLock(key: string, fn: () => Promise<void>) {
  const prev = locks.get(key) ?? Promise.resolve();
  let release: () => void;
  const current = new Promise<void>((res) => (release = res));
  locks.set(key, prev.then(() => current));

  try {
    await prev;
    await fn();
  } finally {
    release!();
    if (locks.get(key) === current) locks.delete(key);
  }
}

async registerLocal(req: AuthLocalReq): Promise<TokenPair> {
  const { username, password } = req;

  return withLock(username, async () => {
    // 이 안에서는 같은 username에 대해 동시에 두 개가 돌지 않음
    const existing = await this.authRepository.findByProviderAndProviderId(
      UserAuthProvider.LOCAL,
      username,
    );
    if (existing) {
      throw new AppError(AppErrorMessage.USER_ALREADY_EXISTS, 409, AppErrorCode.CONFLICT);
    }

    const hashedPassword = await bcrypt.hash(password, this.SALT_ROUNDS);
    const auth = await this.authRepository.create(
      UserAuthProvider.LOCAL,
      username,
      hashedPassword,
    );
    // 기존과 동일한 로직
    return tokenPair;
  });
}
```

만약에 동시에 동일한 username이 N개가 들어온다면,

- 1번째 요청 : `prev = Promise.resolve()` -> `fn()` 회원가입 로직 실행
- 2번째 요청 : `prev` = 1번째 요청 -> 1번이 `release()` 할 때까지 대기하다가 그 다음에 `fn()` 회원가입 로직 실행
- 3번째 요청 : 2번째 요청이 끝날 때까지 대기하다가 실행
- .... 이런식으로 동일한 username은 하나 씩만 회원가입 로직을 실행

그래서 `check-then-act`가 동시에 겹치지 않고, 순차적으로 실행된다는 장점이 있기 때문에 저의 테스트 시나리오에서는 1명만 201, 99명은 `409(CONFLICT)`라는 결과가 나오게 됩니다.

#### 예방법5. 분산 락 (Redis)

Redis를 외부 저장소 느낌으로 사용해서, `SETNX`(set if not exists) 방식으로 username 단위 락을 걸어 두는 방법입니다.
만약에 회원가입 로직을 수행해주는 인스턴스가 여러 개 있어도 같은 Redis를 바라보게만 한다면, 해당 username은 한 군데에서만 처리한다는 것을 보장할 수 있게 됩니다.

```typescript
const lockKey = `signup:${username}`;

//만약 해당 username이 존재하지 않는다면, redis에 set이 되고, true가 된다. 하지만, 이미 username이 존재한다면, null을 반환
const acquired = await redis.set(lockKey, '1', { NX: true, EX: 5 });

if (!acquired) {
  throw new AppError('이미 가입 처리 중입니다.', 409);
}

try {
  //회원가입 로직
  const existing = await this.authRepository.findByProviderAndProviderId(
    UserAuthProvider.LOCAL,
    username,
  );
  if (existing) {
    throw new AppError(AppErrorMessage.USER_ALREADY_EXISTS, 409, AppErrorCode.CONFLICT);
  }
  const hashedPassword = await bcrypt.hash(password, this.SALT_ROUNDS);
  const auth = await this.authRepository.create(/* ... */);
  return tokenPair;
} finally {
  await redis.del(lockKey); //락 해제
}
```

하지만 별도로 Redis라는 인프라가 필요해지고, 만료(EX) 설정이 짧으면 작업이 길 때 풀려 버리고, 길면 장애 시 오래 잡혀 있을 수 있어서 복구 전략을 고민해야 한다는 단점이 있습니다(그냥 일이 늘어남^^)

## 만약 대응 한다면?

이미 DB에 Unique 제약이 걸려 있기 때문에 **데이터 무결성**은 보장이 되고 있었습니다. 그리고 문제점은 "DB가 던진 에러를 그대로 500으로 넘겨준다"는 점이었죠. PostgreSQL은 Unique 제약 위반 시에 `23505`라는 에러 코드를 주기 때문에, 이 에러 코드를 catch해서, `409(CONFLICT)`로 주면 됩니다.

## 현재 나에게 맞는 방법은?

저는 결국에 대응하는 쪽을 선택하였습니다.

- 이미 DB 제약이 걸려 있었기 때문에, 중복 저장까지 되는 대참사는 막을 수 있었고,
- 동시에 같은 username으로 요청하는 일 자체가 드문 상황이고,
- 락킹(Locking)이나 Redis를 활용한다는 것 자체가 너무 과한 오버엔지니어링이라고 판단 했습니다.
- 예방법1(로직 자체를 바꾸자 : `check-then-act`이 아니라 **한 번에 처리**)과 예방법4(애플리케이션 레벨 락)도 좋은 방법이었지만, 새롭게 로직을 추가해야 한다는 장점이 있었습니다.

그래서 완벽하게 막는 것보다는 문제가 생겼을 때 제대로 처리하는 쪽이 더 맞다고 생각했습니다.

## 마무리

`catch` 블록에서 PostgreSQL 에러 코드 `23505`만 골라서 409(CONFLICT)로 바꿔줄 수 있도록 2중 나생문까지 만들었습니다.

![소환술]({{ '/assets/images/2026-02-11-0_0.jpg' }})
![3중나생문]({{ '/assets/images/2026-02-11-0_1.webp' }})

```typescript
async registerLocal(req: AuthLocalReq): Promise<TokenPair> {
  const { username, password } = req;

  // 1차 방어: 일반적인 상황에서의 중복 체크
  const existingAuth = await this.authRepository.findByProviderAndProviderId(
    UserAuthProvider.LOCAL,
    username,
  );

  // 만약 존재하는 사용자라면, 409(CONFLICT) 에러 던짐
  if (existingAuth) {
    throw new AppError(
      AppErrorMessage.USER_ALREADY_EXISTS,
      409,
      AppErrorCode.CONFLICT
    );
  }

  // 비밀번호 암호화
  const hashedPassword = await bcrypt.hash(password, this.SALT_ROUNDS);
  const queryRunner = this.dataSource.createQueryRunner();
  await queryRunner.connect();
  await queryRunner.startTransaction();

  try {
    const auth = await this.authRepository.create(
      UserAuthProvider.LOCAL,
      username,
      hashedPassword,
    );

    const tokenPair = await this.generateAndStoreTokens(auth.id);
    await queryRunner.commitTransaction();

    return {/*...*/};
  } catch (error) {
    await queryRunner.rollbackTransaction();

    // 2차 방어: Race Condition 때문에 발생한 에러 핸들링
    const dbError = error as { code?: string };

    // PostgreSQL Unique Violation 에러 코드는 23505임
    if (dbError.code === '23505') {
      throw new AppError(
        AppErrorMessage.USER_ALREADY_EXISTS,
        409,
        AppErrorCode.CONFLICT
      );
    }

    throw error;
  } finally {
    await queryRunner.release();
  }
}
```

처음에는 그냥 호기심이었지만, 이 호기심 덕분에 동시성이라는 아주아주아주아주 좋은 경험을 할 수 있었습니다.
