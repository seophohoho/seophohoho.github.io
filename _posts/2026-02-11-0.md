## 시작하며

저는 사이드 프로젝트 poposafari의 서버를 `Node.js`로 개발하고 있습니다. 어느 날 로컬 회원가입 로직을 검토하다가 문득 이런 생각이 들었습니다.

> "같은 username으로 두 명이 동시에 가입 버튼을 누르면 어떻게 될까?"
{: .callout .question}

중복 체크 로직이 있으니 당연히 한 명만 `201`, 나머지는 `409(CONFLICT)`를 받겠지 싶었습니다. 하지만 확신이 서지 않아서 직접 테스트해보기로 했습니다.

해당 이슈의 결론부터 말씀드리면, **PostgreSQL의 Unique 제약 위반 에러(`23505`)를 `catch`해서 `409`로 변환**하는 방식으로 해결할 수 있었습니다.
중복 체크 로직이 있는데 왜 `409`가 아닌 `500`이 떴을까요? 궁금하시지 않나요?

이 글을 통해 다음 내용을 가져가실 수 있습니다.

1. `check-then-act` 패턴이 비동기 환경에서 왜 위험한지
2. Race Condition을 예방하는 다양한 방법과 각각의 트레이드오프
3. 문제 상황에서 어떤 기준으로 해결책을 선택했는지

## 문제의 시작 — 중복 체크가 있는데 왜 500이?

### 기존 회원가입 로직

제가 작성한 회원가입 로직은 `check-then-act` 패턴입니다. 먼저 \"이미 있는 유저인가?\"를 확인(`check`)하고, 없다면 회원가입(`act`)하는 흐름입니다.

```typescript
async registerLocal(req: AuthLocalReq): Promise<TokenPair> {
  const { username, password } = req;

  // check: 이미 존재하는 username인가?
  const existingAuth = await this.authRepository.findByProviderAndProviderId(
    UserAuthProvider.LOCAL,
    username,
  );

  // 존재한다면 409(CONFLICT) 에러 던짐
  if (existingAuth) {
    throw new AppError(AppErrorMessage.USER_ALREADY_EXISTS, 409, AppErrorCode.CONFLICT);
  }

  // act: 없으니 회원가입 수행
  const hashedPassword = await bcrypt.hash(password, this.SALT_ROUNDS);
  const queryRunner = this.dataSource.createQueryRunner();
  await queryRunner.connect();
  await queryRunner.startTransaction();

  try {
    const auth = await this.authRepository.create(
      UserAuthProvider.LOCAL,
      username,
      hashedPassword,
    );
    const tokenPair = await this.generateAndStoreTokens(auth.id);
    await queryRunner.commitTransaction();
    return {/*...*/};
  } catch (error) {
    await queryRunner.rollbackTransaction();
    throw error;
  } finally {
    await queryRunner.release();
  }
}
```

순차적으로 요청이 들어온다면 전혀 문제가 없는 코드입니다. 그래서 **동시에 요청이 몰리는 상황**을 직접 만들어 검증해보기로 했습니다.

### 동시에 100번 요청 보내기

`Promise.all`을 이용해서 동일한 `username`으로 100개의 요청을 동시에 보내는 테스트 코드를 작성했습니다.

> `k6` 같은 부하 테스트 도구도 있지만, 제가 확인하고 싶었던 건 단 하나 — **\"내 로직이 동시 요청에서 의도대로 동작하는가\"** 였기 때문에 `Promise.all`로 충분하다고 판단했습니다.

```typescript
const url = '로컬 회원가입 API 주소';
const payload = { username: 'testuser123', password: 'password123' };

// 100개의 요청을 동시에 발사
const reqs = Array.from({ length: 100 }, () =>
  axios.post(url, payload).catch((err) => err.response),
);

const res = await Promise.all(reqs);
const summary = res.reduce((acc, r) => {
  const status = r.status || 'What?';
  acc[status] = (acc[status] || 0) + 1;
  return acc;
}, {});

console.table(
  Object.entries(summary).map(([status, count]) => ({
    'HTTP Status': status,
    Count: count,
    Result: status === '201' ? 'SUCCESS' : status === '409' ? 'CONFLICT' : 'UNKNOWN',
  })),
);
```

예상한 결과는 간단했습니다. **1개는 `201`, 나머지 99개는 `409(CONFLICT)`**.

### 그런데 결과는?

```bash
┌─────────┬─────────────┬───────┬───────────┐
│ (index) │ HTTP Status │ Count │ Result    │
├─────────┼─────────────┼───────┼───────────┤
│ 0       │ '201'       │ 1     │ 'SUCCESS' │
│ 1       │ '500'       │ 99    │ 'UNKNOWN' │
└─────────┴─────────────┴───────┴───────────┘
```

`409`가 아니라 `500`이 99개 찍혀 있었습니다. 서버 로그를 확인해보니 에러는 DB에서 나고 있었습니다.

```bash
POST /api/auth/register/local 500 1730.163 ms - 165
{
    severity: 'ERROR',
    code: '23505',
    detail: 'Key (provider, provider_id)=(local, testuser123) already exists.',
    table: 'auth_identities',
    constraint: 'IDX_b4756e087ec67d0abe2f53792a',
}
```

PostgreSQL의 **Unique 제약 조건 위반 에러(`23505`)**였습니다. 다행히 `username`을 유니크 키로 지정해 두어서 중복 데이터 저장은 막았지만, 사용자 입장에서는 \"서버에 문제가 생겼구나\"라는 오해를 줄 수 있는 `500` 에러를 받게 된 셈이었습니다.

## 왜 이런 일이 발생했을까?

원인은 두 가지가 맞물렸습니다. **`check-then-act` 패턴의 구조적 한계**와, 그 패턴이 **Node.js의 비동기 환경 위에서 동작**한다는 점입니다.

### check-then-act의 시간 텀

`check-then-act` 패턴은 이름 그대로 \"상태를 확인(check)한 뒤, 그 결과를 믿고 행동(act)하는\" 코드 패턴입니다. 문제는 이 두 단계 사이에 항상 작은 **시간 텀**이 존재한다는 점입니다.

체크할 때는 조건에 부합했더라도, 행동하려는 찰나에 다른 요청이 먼저 들어와 상태를 바꿔버릴 수 있습니다.

### Node.js 비동기 처리가 더한 기름

Node.js는 싱글 스레드 기반이지만, DB 조회 같은 I/O 작업은 비동기로 처리합니다. 덕분에 한 요청이 중복 체크를 위해 DB에 질의해 두고 응답을 기다리는 동안에도, 다른 요청들이 계속 들어와 같은 조회를 수행할 수 있습니다.

그 결과, 100개의 요청이 **거의 동시에 중복 체크를 통과**하는 상황이 만들어졌습니다.

```
Request 1:   [중복 체크 ✓] -----> [INSERT ✓]
Request 2:   [중복 체크 ✓] -----> [INSERT ✗] (Unique 제약 위반!)
Request 3:   [중복 체크 ✓] -----> [INSERT ✗] (Unique 제약 위반!)
...
Request 100: [중복 체크 ✓] -----> [INSERT ✗] (Unique 제약 위반!)
```

체크 시점에는 아직 아무도 `INSERT`를 하지 않았기 때문에, 모든 요청이 \"없다\"고 판단하고 저장 단계로 넘어갑니다. 그중 가장 먼저 `INSERT`에 성공한 1개를 제외한 나머지는 DB Unique 제약에 걸려 `500`이 된 겁니다.

여기까지 읽으셨다면, 어떤 해결책이 떠오르시나요?

## 해결 방법 탐색 — 예방할 것인가, 대응할 것인가?

크게 두 갈래로 나뉘었습니다.

- **예방 (Prevention)**: Race Condition 자체가 발생하지 않도록 막는 방법
- **대응 (Handling)**: 발생한 에러를 제대로 잡아서 사용자에게 적절한 응답을 주는 방법

### #1 로직 자체를 바꾸기 — check-then-act를 한 방에 처리

`SELECT` → `INSERT`로 두 번 쿼리를 보내는 대신, DB에서 한 번에 처리하도록 바꾸는 방법입니다.

```sql
-- ON CONFLICT: 중복이면 아무것도 하지 않고, RETURNING으로 결과 확인
INSERT INTO auth_identities (provider, provider_id, password)
VALUES ('local', $username, $hashedPassword)
ON CONFLICT (provider, provider_id) DO NOTHING
RETURNING id;
```

`RETURNING id`에 값이 있으면 회원가입 성공, 없으면 이미 존재하는 `username`이라고 판단해서 `409`를 반환합니다. `check`와 `act` 사이의 시간 텀 자체를 없애버리는 방법이라 근본적인 해결책입니다.

다만 기존 `check-then-act` 로직을 통째로 교체해야 한다는 단점이 있습니다.

### #2 비관적 락 (Pessimistic Lock)

동시성 문제 하면 빠지지 않는 **비관적 락 (Pessimistic Lock)**을 적용해보는 방법입니다.

```typescript
// SELECT ... FOR UPDATE로 조회한 row에 락을 건다
const existing = await queryRunner.manager.findOne(User, {
  where: { username },
  lock: { mode: 'pessimistic_write' },
});
```

`lock: { mode: 'pessimistic_write' }`는 내부적으로 `SELECT ... FOR UPDATE`를 사용합니다. 이 쿼리가 **조회된 row에 row-level lock**을 걸어, 락을 먼저 잡은 트랜잭션이 `COMMIT` 또는 `ROLLBACK`할 때까지 다른 트랜잭션을 블로킹시킵니다.

그런데 생각해보면, 지금 시나리오는 **아직 존재하지 않는 `username`에 대한 동시 가입**입니다. 락을 걸 **row 자체가 없기 때문에**, 결국 같은 `INSERT` 충돌이 발생하고 맙니다.

> 비관적 락은 이미 존재하는 row를 여러 트랜잭션이 동시에 수정하려 할 때 유효합니다. INSERT 충돌 상황에는 맞지 않는 방법이었습니다.

### #3 낙관적 락 (Optimistic Lock)

낙관적 락은 데이터를 읽을 때 락을 걸지 않고, `UPDATE` 시점에 버전을 비교해 충돌 여부를 판단하는 방식입니다.

```typescript
@Entity('auth_identities')
export class Auth {
  @PrimaryGeneratedColumn({ type: 'bigint' })
  id!: string;

  @VersionColumn() // UPDATE 시 version + 1
  version: number;
}
```

하지만 이 방법도 마찬가지입니다. `UPDATE`할 row 자체가 없는 신규 `INSERT` 상황에서는 버전 비교가 의미가 없습니다. 역시 이 시나리오에는 맞지 않는 도구였습니다.

### #4 애플리케이션 레벨 락

서버 메모리에 `Map`을 두고, 같은 `username`에 대해서는 한 번에 하나의 회원가입 로직만 실행하도록 직렬화하는 방법입니다.

```typescript
const locks = new Map<string, Promise<void>>();

async function withLock(key: string, fn: () => Promise<void>) {
  const prev = locks.get(key) ?? Promise.resolve();
  let release: () => void;
  const current = new Promise<void>((res) => (release = res));
  locks.set(key, prev.then(() => current));

  try {
    await prev;  // 이전 요청이 끝날 때까지 대기
    await fn();
  } finally {
    release!();
    if (locks.get(key) === current) locks.delete(key);
  }
}

async registerLocal(req: AuthLocalReq): Promise<TokenPair> {
  const { username, password } = req;

  return withLock(username, async () => {
    // 같은 username에 대해 동시에 두 개가 실행되지 않음
    const existing = await this.authRepository.findByProviderAndProviderId(
      UserAuthProvider.LOCAL,
      username,
    );
    if (existing) {
      throw new AppError(AppErrorMessage.USER_ALREADY_EXISTS, 409, AppErrorCode.CONFLICT);
    }
    // ... 이하 동일
  });
}
```

동일한 `username`으로 요청이 N개 들어오면:

- 1번째 요청: 즉시 실행
- 2번째 요청: 1번이 `release()` 할 때까지 대기 후 실행
- 3번째 요청: 2번이 끝날 때까지 대기 후 실행

이렇게 `check-then-act`가 username 단위로 직렬화되기 때문에, 1명은 `201`, 나머지는 정확히 `409(CONFLICT)`를 받게 됩니다. 하지만 **단일 인스턴스 한정**이라는 제약이 있습니다.

### #5 분산 락 (Redis)

`Redis`를 외부 저장소로 활용해 `SETNX`(set if not exists) 방식으로 `username` 단위 락을 거는 방법입니다.

```typescript
const lockKey = `signup:${username}`;
// NX: 이미 있으면 null 반환, EX: 5초 후 자동 만료
const acquired = await redis.set(lockKey, '1', { NX: true, EX: 5 });

if (!acquired) {
  throw new AppError('이미 가입 처리 중입니다.', 409);
}

try {
  // 회원가입 로직
} finally {
  await redis.del(lockKey); // 락 해제
}
```

인스턴스가 여러 개 있어도 같은 Redis를 바라보면 username 단위 직렬화가 보장됩니다. 하지만 Redis라는 **별도 인프라가 필요**하고, `EX` 설정이 짧으면 작업 도중 락이 풀리고, 길면 장애 시 오래 잡혀있는 문제가 생깁니다. 복구 전략까지 고민해야 하니 일이 늘어납니다.

## 제가 선택한 방법 — 예방보다 대응

저는 결국 **대응 방향**을 선택했습니다.

- 이미 DB에 Unique 제약이 걸려 있어 **중복 데이터 저장이라는 대참사는 막혀 있었습니다.**
- 동시에 동일한 `username`으로 가입 요청이 오는 상황 자체가 **매우 드문 케이스**였습니다.
- 락킹이나 Redis는 지금 이 문제에 비해 **오버엔지니어링**이라고 판단했습니다.
- #1(한 번에 처리)과 #4(애플리케이션 레벨 락)도 좋은 방법이었지만, **새 로직을 추가**해야 한다는 비용이 있었습니다.

DB 무결성은 이미 지켜지고 있었으니, \"완벽하게 막는 것\"보다 \"문제가 생겼을 때 제대로 처리하는 것\"이 지금 맥락에 더 맞다고 판단했습니다.

PostgreSQL은 Unique 제약 위반 시 에러 코드 `23505`를 던집니다. 이 코드를 `catch`에서 잡아 `409(CONFLICT)`로 변환해주면 됩니다.

## 해결책 적용

`catch` 블록에서 PostgreSQL 에러 코드 `23505`를 골라내어 `409`로 바꿔주는 **2차 방어선**을 추가했습니다.

![소환술]({{ '/assets/images/2026-02-11-0_0.jpg' }})
![2중 나생문]({{ '/assets/images/2026-02-11-0_1.webp' }})

```typescript
async registerLocal(req: AuthLocalReq): Promise<TokenPair> {
  const { username, password } = req;

  // 1차 방어: 일반적인 상황에서의 중복 체크
  const existingAuth = await this.authRepository.findByProviderAndProviderId(
    UserAuthProvider.LOCAL,
    username,
  );

  if (existingAuth) {
    throw new AppError(AppErrorMessage.USER_ALREADY_EXISTS, 409, AppErrorCode.CONFLICT);
  }

  const hashedPassword = await bcrypt.hash(password, this.SALT_ROUNDS);
  const queryRunner = this.dataSource.createQueryRunner();
  await queryRunner.connect();
  await queryRunner.startTransaction();

  try {
    const auth = await this.authRepository.create(
      UserAuthProvider.LOCAL,
      username,
      hashedPassword,
    );
    const tokenPair = await this.generateAndStoreTokens(auth.id);
    await queryRunner.commitTransaction();
    return {/*...*/};
  } catch (error) {
    await queryRunner.rollbackTransaction();

    // 2차 방어: Race Condition으로 발생한 Unique 제약 위반 에러 핸들링
    const dbError = error as { code?: string };
    if (dbError.code === '23505') {
      throw new AppError(AppErrorMessage.USER_ALREADY_EXISTS, 409, AppErrorCode.CONFLICT);
    }

    throw error;
  } finally {
    await queryRunner.release();
  }
}
```

적용 후 동일한 테스트를 다시 돌려보았습니다.

**Before**

```bash
┌─────────┬─────────────┬───────┬───────────┐
│ (index) │ HTTP Status │ Count │ Result    │
├─────────┼─────────────┼───────┼───────────┤
│ 0       │ '201'       │ 1     │ 'SUCCESS' │
│ 1       │ '500'       │ 99    │ 'UNKNOWN' │
└─────────┴─────────────┴───────┴───────────┘
```

**After**

```bash
┌─────────┬─────────────┬───────┬──────────────┐
│ (index) │ HTTP Status │ Count │ Result       │
├─────────┼─────────────┼───────┼──────────────┤
│ 0       │ '201'       │ 1     │ 'SUCCESS'    │
│ 1       │ '409'       │ 99    │ 'CONFLICT'   │
└─────────┴─────────────┴───────┴──────────────┘
```

1개는 성공, 99개는 의도한 대로 `409(CONFLICT)`를 받게 되었습니다.

## 마치며

지금 돌이켜보면, `23505` 에러 코드 하나만 잡아도 되는 간단한 문제였습니다. 하지만 그 결론에 도달하기까지 비관적 락, 낙관적 락, 분산 락을 하나씩 검토하면서 왜 각 방법이 이 상황에 맞지 않는지를 직접 따져볼 수 있었습니다.

처음에 저는 \"중복 체크가 있으니 당연히 안전하겠지\"라고 가정했습니다. 그 가정을 의심하지 않았다면, `check-then-act` 패턴이 비동기 환경에서 가진 취약점을 그냥 모르고 넘어갔을 겁니다.

**에러 코드는 증상일 뿐이고, 진짜 원인은 그 아래에 있습니다.** 단순한 호기심 하나가 동시성이라는 깊은 주제를 탐험하게 해준 좋은 경험이었습니다.
