## 시작하며

저는 사이드 프로젝트 poposafari의 실시간 이동 기능에 **Batch Packet Sending**을 적용하여 CPU 사용량을 줄인 바 있습니다. 최적화까지 마쳤으니 이제 아무 문제가 없겠다 싶었는데, 마지막으로 기능 테스트를 한 번 더 돌려보았습니다.

![좌표가 꼬인 화면]({{ site.img_path }}/2026-03-18-0_0.png)

잘 저장되던 플레이어의 좌표가 어느 순간부터 서버 좌표와 클라이언트 화면의 좌표가 달라지는 문제를 발견했습니다.

해당 문제의 결론부터 말씀드리면, **좌표를 Redis가 아닌 Node.js 메모리(Map)에서 직접 관리**하는 방식으로 전환하여 Race Condition을 구조적으로 제거할 수 있었습니다.
"Redis read → 좌표 계산 → Redis write"라는 흐름이 왜 동시성 문제를 일으킬 수밖에 없었는지 궁금하시지 않나요?

이 글을 통해 다음 내용을 가져가실 수 있습니다.

1. Node.js 이벤트 루프에서 비동기 `await`가 어떻게 Race Condition을 만들어내는지
2. 동시성 문제를 해결하는 다양한 방법과 각각의 트레이드오프
3. 빈번한 이벤트에서 외부 I/O 의존도를 줄이는 방향으로 설계를 전환한 이유

## 문제 발견 - 분명히 이동했는데 서버 좌표가 뒤처진다

### 기존 move 이벤트 처리 흐름

poposafari는 타일 맵 기반 게임이고, 클라이언트에서는 사용자가 이동할 때마다 `direction`(방향)과 `moveType`(이동 방식)을 담아 `move` 이벤트를 서버에 `emit`하도록 구현되어 있습니다.

```typescript
// 클라이언트 — 이동 시 서버에 move 이벤트 전송
private emitMoveToServer(dir: DIRECTION): void {
  if (dir === DIRECTION.NONE) return;
  socket.emit('move', {
    direction: dir as MovePayload['direction'],
    moveType,
  });
}
```

> 타일 맵 기반 게임이란, 맵 전체가 격자 형태의 타일로 구성되어 있고 각 타일마다 좌표가 부여된 방식입니다. 플레이어는 타일 단위로 이동하며, 예를 들어 (10,20)에 있는 플레이어가 오른쪽으로 한 칸 이동하면 (11,20)으로 옮겨집니다.
> {: .callout .info}

그리고 서버는 클라이언트로부터 `move` 이벤트를 받으면 아래 흐름으로 처리합니다.

1. **유효성 검사** — `direction`, `moveType` 값 검증
2. **상태 조회** — Redis에서 현재 좌표(`x`, `y`)와 `lastMoveTime` 조회
3. **좌표 계산** — `direction`에 따라 새 좌표 계산
4. **상태 저장** — Redis에 변경된 좌표 저장
5. **배치 버퍼에 추가** — `moveBuffer`에 저장
6. **배치 브로드캐스트** — 50ms tick 루프에서 `users_moved`로 일괄 전송

```typescript
// 서버 — move 이벤트 핸들러 (핵심 부분만 발췌)
socket.on("move", async (payload) => {
  const direction = parsed?.direction;
  if (!direction || !MOVE_DIRECTIONS.includes(direction)) return;

  // 1) Redis에서 현재 좌표 조회
  const state = await getUserState(userId);
  if (!state) return;

  let curX = Number(state.x);
  let curY = Number(state.y);

  // 2) direction에 따라 좌표 계산
  const step = moveType === "jump" ? 2 : 1;
  switch (direction) {
    case "up":
      curY -= step;
      break;
    case "down":
      curY += step;
      break;
    case "left":
      curX -= step;
      break;
    case "right":
      curX += step;
      break;
  }

  // 3) Redis에 변경된 좌표 저장
  await updateUserStatePosition(userId, {
    x: String(curX),
    y: String(curY),
    lastMoveTime: new Date().toISOString(),
  });

  // 4) 배치 버퍼에 추가 → 50ms마다 브로드캐스트
  this.moveBuffer.get(roomId)!.set(userId, {
    x: curX,
    y: curY,
    direction,
    moveType,
  });
});
```

순차적으로 이벤트가 들어온다면 문제없는 코드입니다. 그런데 실제 플레이 환경에서는 이야기가 달랐습니다.

## 첫 번째 가설 — 패킷 유실?

테스트 당시 상황은 이랬습니다. 왼쪽 브라우저는 유저 A, 오른쪽 브라우저는 유저 B로 접속한 상태에서, 유저 B만 이동시켰습니다.

| 위치                           | 좌표    | 설명                       |
| ------------------------------ | ------- | -------------------------- |
| **유저 A 화면에서 본 유저 B**  | (33,27) | 서버가 브로드캐스트한 좌표 |
| **Redis에 저장된 유저 B 좌표** | (33,27) | 서버가 최종 기록한 좌표    |
| **유저 B 화면에서 본 유저 B**  | (35,27) | 클라이언트 자체 좌표       |

유저 B 화면의 좌표(35,27)가 서버 좌표(33,27)보다 2칸 앞서 있었습니다. 처음에는 이렇게 생각했습니다.

> "유저 B의 move 이벤트 2개가 네트워크에서 유실된 것 아닐까?"
> {: .callout .question}

패킷이 유실된 것인지, 서버가 받고도 처리를 잘못한 것인지 확인이 필요했습니다.

## 로그를 찍어 패킷 유실 여부 확인

확인을 위해 `move` 핸들러에 디버그 로그를 추가하여, 이벤트 도착 시점, Redis에서 읽은 좌표, 계산 후 저장한 좌표를 각각 기록하도록 했습니다.

```typescript
socket.on("move", async (payload) => {
  // 이벤트 도착 시점 로그
  logger.info(`player(${userId}) move ${direction} + ${moveType}`);

  const state = await getUserState(userId);
  const readX = Number(state.x);
  const readY = Number(state.y);

  // 좌표 계산 ...

  await updateUserStatePosition(userId, { x: String(curX), y: String(curY) });

  // Redis에서 읽은 좌표 → 계산 후 저장한 좌표 로그
  logger.info(
    `[MOVE-DEBUG] userId=${userId} dir=${direction} read=(${readX},${readY}) -> wrote=(${curX},${curY})`,
  );
});
```

유저 B를 오른쪽으로 9칸 이동시켜보았고, 로그 결과는 아래와 같았습니다.

```bash
# 1번: move#1 이벤트 도착
{"message":"player(2168) move right + running","timestamp":"2026-03-18 07:04:44"}
# 2번: move#2 이벤트 도착 (move#1의 Redis 처리가 끝나기 전에!)
{"message":"player(2168) move right + running","timestamp":"2026-03-18 07:04:44"}
# 3번: move#1 → read=(16,26) -> wrote=(17,26)
{"message":"[MOVE-DEBUG] userId=2168 dir=right read=(16,26) -> wrote=(17,26)","timestamp":"2026-03-18 07:04:45"}
# ...
# 5번: move#2 → read=(16,26) -> wrote=(17,26) ← 같은 좌표를 읽음!
{"message":"[MOVE-DEBUG] userId=2168 dir=right read=(16,26) -> wrote=(17,26)","timestamp":"2026-03-18 07:04:45"}
# ...
# 22번: move#8 이벤트 도착
{"message":"player(2168) move right + running","timestamp":"2026-03-18 07:04:46"}
# 23번: move#9 이벤트 도착 (연달아 도착)
{"message":"player(2168) move right + running","timestamp":"2026-03-18 07:04:46"}
# 24번: move#8 → read=(22,26) -> wrote=(23,26)
{"message":"[MOVE-DEBUG] userId=2168 dir=right read=(22,26) -> wrote=(23,26)","timestamp":"2026-03-18 07:04:46"}
# 26번: move#9 → read=(22,26) -> wrote=(23,26) ← 또 같은 좌표를 읽음!
{"message":"[MOVE-DEBUG] userId=2168 dir=right read=(22,26) -> wrote=(23,26)","timestamp":"2026-03-18 07:04:46"}
```

`player(2168) move right + running` 로그가 정확히 9줄 찍혔고, 이는 **패킷은 유실되지 않았다**는 것을 의미했습니다.  
그런데 이상합니다. 9번의 이벤트가 모두 서버에 도달했는데, 왜 서버는 7칸만 이동시킨 걸까요?

로그를 자세히 보면 **같은 좌표를 두 번 읽는 구간이 2곳**을 발견할 수 있는데,

- **첫 번째 충돌**: move#1과 move#2가 동일한 `(16,26)`을 읽어 둘 다 `(17,26)`을 씀 → **1칸 손실**
- **두 번째 충돌**: move#8과 move#9가 동일한 `(22,26)`을 읽어 둘 다 `(23,26)`을 씀 → **1칸 손실**

결과적으로 9번 이동에서 총 2번의 이동이 씹혀 2칸이 손실된 것이었습니다.

## 왜 이런 일이 발생했을까? — Node.js 이벤트 루프와 await

감을 잡으신 분들도 있고 아직 아리송하신 분들도 있으실 것 같습니다. 원인을 이해하려면, Node.js의 이벤트 루프와 `await`의 동작 방식을 이해해야 합니다.

Node.js는 싱글 스레드지만 DB, 네트워크 같은 I/O 작업은 비동기로 처리합니다. `await getUserState(userId)`를 만나는 순간, 해당 async 함수는 **suspend(일시 중단)**되고 콜 스택이 비워집니다. 그러면 이벤트 루프는 큐에 대기 중인 다음 콜백(다음 `move` 이벤트)을 즉시 실행하게 됩니다.

```plain
poll phase 큐: [move#1 콜백, move#2 콜백]

1. move#1 실행 시작
2. await getUserState(userId) → Redis 요청 전송, async 함수 suspend
3. 콜 스택이 비워짐 → 이벤트 루프가 다음 콜백 실행
4. move#2 실행 시작
5. await getUserState(userId) → 아직 move#1의 write가 끝나지 않았으므로
   같은 좌표 (16,26)을 읽어버림!
6. move#1의 Redis 응답 도착 → (17,26) 저장
7. move#2의 Redis 응답 도착 → (16,26)을 읽었으니 마찬가지로 (17,26) 저장
   → 1칸 손실!
```

**read → modify → write** 사이에 다른 move 이벤트가 끼어들 수 있는 구조, **Race Condition** 문제였습니다.

## 해결 방법 탐색 — 동시성을 제어할 것인가, 구조를 바꿀 것인가?

저는 이 문제를 Race Condition 자체가 발생하지 않도록 동시성을 제어하는 쪽으로만 먼저 생각을 했었습니다. 하지만, 조금 더 생각을 해보면...  
`move`는 유저가 한 칸 움직일 때마다 발생하고, 제 서비스 특성상 정말정말정말 자주 일어날 수 밖에 없는 이벤트입니다. 유저가 100명이 동시에 플레이하면 초당 수백 ~ 수천 번 발생할 수 있습니다. 그런데 지금 구조에서는 이 `move` 이벤트 한 번마다 Redis 왕복이 **2회(read 1회 + write 1회)** 일어나고 있었습니다. 외부 I/O(Redis)가 항상 빠르다는 보장은 없기 때문에, 혹시라도 네트워크가 순간적으로 느려질 경우 `await` 구간이 길어지고, read-write 사이에 다른 move 이벤트가 끼어들 확률이 그만큼 올라가게 됩니다. 다시 말해, 지금의 Race Condition은 Redis가 조금이라도 느려지면 언제든 재현될 수 있는 **구조적인 문제**였습니다.

> "동시성 문제를 막는 것도 중요하지만, 그 전에 빈번한 이벤트가 외부 I/O에 매번 의존하는 구조 자체를 다시 생각해볼 필요가 있었습니다."
> {: .callout .info}

그래서 저는 크게 두 방향을 잡기로 하였습니다.

- **방향 1**: Race Condition이 발생하지 않도록 동시성을 제어하는 방법
- **방향 2**: Redis 의존도 자체를 줄여 Race Condition이 구조적으로 발생하지 않도록 만드는 방법

### #2 방향 1 — 동시성 제어

**유저별 Promise Chain**은 가장 단순한 접근입니다. 같은 유저의 move 이벤트가 순차 실행되도록 이전 Promise가 resolve된 뒤에 다음 이벤트가 시작되게 강제합니다.

```typescript
const userLocks = new Map<string, Promise<void>>();

function withUserLock(userId: string, fn: () => Promise<void>): void {
  const prev = userLocks.get(userId) ?? Promise.resolve();
  const next = prev.then(fn).catch(() => {});
  userLocks.set(userId, next);
}

socket.on("move", (payload) => {
  withUserLock(userId, async () => {
    const state = await getUserState(userId); // Redis read
    const { curX, curY } = calcPosition(state, direction, moveType);
    await updateUserStatePosition(userId, curX, curY); // Redis write
    this.moveBuffer.get(roomId)!.set(userId, { x: curX, y: curY });
  });
});
```

변경점이 적고 Race Condition은 확실히 막을 수 있었지만, Redis 왕복 2회는 그대로 남아 있게 됩니다. Redis가 느려지면 해당 유저의 후속 move가 전부 큐에 밀리고, 지연이 연쇄적으로 전파 될 것입니다. 그 외에도 **Redis 분산 락(SET NX)**, **Redis Lua 스크립트**를 사용해서 read, modify, write를 하나의 Lua 스크립트로 묶어 Redis 서버 내부에서 원자적으로 실행할 수 있도록 하기 등 다양한 방법이 있었고, 모두 Race Condition 자체는 해결하지만, **move마다 Redis를 거치는 구조는 바뀌지 않는다**는 공통적인 한계가 있습니다.

### 방향 2 — Redis 의존도 자체를 줄이기

발상을 바꿔보았습니다. move처럼 초당 수백 번 발생하는 이벤트에서, 매번 Redis를 거쳐야 할 이유가 있을까요?

**In-Memory 좌표 관리**는 좌표를 Redis가 아닌 Node.js 메모리(`Map`)에서 직접 관리하는 방식입니다.

```typescript
// 메모리에서 좌표 직접 관리
const userPositions = new Map<string, { x: number; y: number }>();

socket.on("move", (payload) => {
  // await 없이 메모리에서 직접 read-modify-write
  const pos = userPositions.get(userId) ?? { x: 0, y: 0 };

  switch (direction) {
    case "right":
      pos.x += step;
      break;
    case "left":
      pos.x -= step;
      break;
    case "down":
      pos.y += step;
      break;
    case "up":
      pos.y -= step;
      break;
  }

  userPositions.set(userId, pos);
  this.moveBuffer.get(roomId)!.set(userId, { ...pos, direction, moveType });
});

// 50ms tick: 변경된 좌표를 Redis에 일괄 sync
setInterval(async () => {
  // moveBuffer 브로드캐스트
  // 변경된 좌표를 pipeline으로 Redis에 동기화
}, 50);
```

move 핸들러에서 `await`가 완전히 사라지기 때문에, async 함수가 suspend될 일이 없게 됩니다. Race Condition을 "제어"하는 것이 아니라, Race Condition이 **존재하지 않는** 구조가 되는 것입니다.

성능 면에서도 차이가 큽니다. Redis 왕복이 move당 2회에서 0회로 줄어들고, 이미 존재하는 50ms tick 루프에서 변경된 좌표를 한 번에 Redis pipeline으로 sync합니다. 100명 기준으로 초당 Redis 호출이 약 1,000회에서 20회 수준으로 줄어듭니다.

물론 trade-off가 있습니다.

- 프로세스가 죽으면 메모리의 좌표가 날아갑니다. tick마다 Redis에 sync하니 최대 50ms분의 유실이 발생할 수 있습니다.
- 만약 동접자가 늘어 소켓 서버를 스케일 아웃(scale-out) 할 때 프로세스 간 메모리를 공유할 수 없기 때문에, 이를 공유할 방법을 따로 생각해야 했습니다.
- 코드 변경 범위가 move 핸들러뿐 아니라 init, disconnect, tick loop 전반에 걸쳐 가장 넓습니다.

## 선택 — In-Memory 좌표 관리

비교하면 이렇습니다.

| 기준                | Promise Chain | 분산 락   | Lua 스크립트 | Optimistic Lock | **In-Memory**   |
| ------------------- | ------------- | --------- | ------------ | --------------- | --------------- |
| Race Condition 해결 | 확실          | 확실      | 확실         | 확실(재시도)    | **구조적 제거** |
| Redis 왕복/move     | 2회           | 4회       | 1회          | 2~N회           | **0회**         |
| 고부하 시 안정성    | 큐 지연 전파  | move 드롭 | 안정적       | 재시도 폭증     | **안정적**      |
| 멀티 프로세스 대응  | 불가          | 가능      | 가능         | 가능            | 추가 설계 필요  |
| 코드 변경량         | 최소          | 소        | 중           | 중              | **대**          |
| 장애 시 데이터 유실 | 없음          | 없음      | 없음         | 없음            | 최대 50ms       |

저는 **In-Memory 좌표 관리**를 선택했습니다.

- poposafari는 현재 단일 인스턴스로 운영 중이라, 멀티 프로세스 제약이 당장의 문제가 아니었습니다.
- 최대 50ms의 좌표 유실은 게임 특성상 허용 가능한 범위라고 판단했습니다.
- 무엇보다 Race Condition을 "막는" 것이 아니라 "존재하지 않도록 만드는" 쪽이 근본적으로 올바른 방향이라고 생각했습니다.
- 코드 변경량이 크다는 단점이 있지만, 한 번 구조를 바꿔두면 이후 타일 충돌 판정 같은 서버 사이드 로직도 동기적으로 추가할 수 있어 확장성도 높아집니다.

## 해결책 적용 — Before / After

**Before**: move 한 번마다 Redis read -> write

```typescript
socket.on('move', async (payload) => {
  const state = await getUserState(userId);   // Redis read (await)
  const curX = /* 계산 */;
  await updateUserStatePosition(userId, ...); // Redis write (await)
  this.moveBuffer.set(userId, { curX, ... });
});
```

**After**: 메모리에서 동기 처리, Redis는 tick에서 일괄 sync

```typescript
// move 핸들러 — await 없이 동기 처리
socket.on("move", (payload) => {
  const pos = userPositions.get(userId) ?? { x: 0, y: 0 };
  switch (direction) {
    case "right":
      pos.x += step;
      break;
    // ...
  }
  userPositions.set(userId, pos);
  this.moveBuffer.get(roomId)!.set(userId, { ...pos, direction, moveType });
});

// 50ms tick — 브로드캐스트 + Redis sync
setInterval(async () => {
  for (const [roomId, buffer] of this.moveBuffer) {
    if (buffer.size === 0) continue;
    io.to(roomId).emit("users_moved", [...buffer.values()]);
    // pipeline으로 변경된 좌표를 Redis에 일괄 기록
    await syncPositionsToRedis([...buffer.entries()]);
    buffer.clear();
  }
}, 50);
```

수정 후 비슷한 시나리오로 30분간 테스트를 진행해보았습니다.
다행히도, 좌표 불일치가 발생하는 일은 전혀 없었습니다. 그리고 **뜻밖의 수확**이 있었는데, 바로 이전보다 CPU 사용량도 줄어들게 되었다는 점이었습니다.  
(이전 포스팅)[https://seophohoho.github.io/2026/03/08/0.html]에서는 `move` 이벤트마다 동일한 맵에 있는 사용자에게 브로드캐스팅을 날려 `writev` 시스템 콜이 과도하게 호출되어 CPU 병목 문제가 있었고, 이를 패킷 모아 보내기(Batch Packet Sending) 방식을 사용하여 CPU 사용량을 낮출 수 있었습니다.

| 동접  | Before (즉시 broadcast) | After (Batch 50ms) | 절감율 |

| 50명  | 121%                    | 54.7%              | -54.8% |

| 150명 | 151%                    | 104%               | -31.1% |
| 200명 | 118%                    | 110%               | -6.8%  |

아래 표는 `Batch + 외부 I/O(Redis) 의존성을 제거`를 적용하고 나서 CPU 사용량을 비교한 내용입니다.

## 마치며

지금 돌이켜보면, "동시성 제어를 추가하면 되는 문제"가 아니라 "왜 이 이벤트가 매번 외부 I/O에 의존하고 있는가"를 스스로에게 먼저 질문해야 했던 문제였습니다.

처음에 저는 로그를 보기 전까지 패킷 유실을 의심했지만, 데이터가 틀렸으니 네트워크 문제겠지 하는 첫 번째 가설이 틀렸다는 것을 확인하는 데 로그 하나면 충분했습니다. 에러의 증상만 보고 원인을 단정하지 않고, 데이터로 검증하는 것이 얼마나 중요한지 체감할 수 있었습니다.

비슷한 상황, 즉 빈번한 이벤트에서 외부 I/O가 끼어 있다면 한 번쯤 **"이게 꼭 필요한가?"**를 물어보시길 권합니다.
