# 카카오페이 기술 블로그 스타일 글쓰기

이 스킬은 카카오페이 기술 블로그의 글쓰기 패턴을 분석하여, 동일한 톤·구조·전개 방식으로 기술 블로그 포스트를 작성하도록 안내한다.

---

## 핵심 철학: "에러 로그는 원인이 아니라 증상일 뿐이다"

카카오페이 기술 블로그의 핵심은 **결론을 알려주는 글이 아니라, 결론에 도달하기까지의 사고 과정을 보여주는 글**이다. 독자가 "나도 이 상황이면 이렇게 생각했을 것 같다"고 느끼게 만드는 것이 목표다.

---

## 글의 전체 구조 (6단계 내러티브 아크)

카카오페이 블로그 글은 아래 6단계를 따른다. 단, 모든 글이 6단계를 전부 사용하는 것은 아니고, 주제에 따라 3~6단계 사이에서 유연하게 조절한다.

### 1단계: 시작하며 — 맥락 설정과 떡밥 투척

- 필자 자기소개 (팀명 + 이름 + 서비스 한줄 소개)
- 서비스의 성장 맥락을 짧게 깔아준다 ("오픈 후 트래픽이 꾸준히 늘어났고")
- 문제의 존재를 암시하되, 아직 원인은 밝히지 않는다
- **결론을 먼저 한 줄로 스포일**하고, 그 뒤에 "왜 그 결론에 도달했는지 궁금하지 않으세요?" 식의 호기심 유도 문장을 넣는다

> 예시 패턴:
> "해당 이슈의 결론부터 말씀드리면, **(해결책)**을 적용하여 문제를 해결할 수 있었습니다.  
> **(표면적 증상)**과 **(진짜 원인)**이 무슨 상관관계가 있는지 궁금하시지 않나요?"

- 글을 통해 독자가 얻을 수 있는 것을 **번호 리스트로 2~3개** 정리한다
- "예상치 못한 병목 구간을 발견하고 진짜 원인을 찾기 위한 과정을 생생하게 담아보았습니다" 같은 마무리

### 2단계: 첫 에러 발생 — 증상 묘사

- 에러 로그 / 스크린샷을 **가장 먼저** 보여준다 (독자의 시선 고정)
- 에러 메시지의 의미를 소스 코드 레벨까지 파고들어 설명한다
- 해당 시점에서 팀이 어떤 **첫 번째 가설**을 세웠는지 서술한다
- 인용 블록(`>`)으로 당시의 사고를 독백처럼 담는다

> 예시:
>
> > 커넥션 풀이 부족한 건가? 커넥션에 여유가 생기면 획득하려 대기하는 시간도 없어질 테니 자연스럽게 초기 응답 속도 지연도 해결되지 않을까?

### 3단계: 시도 #N — 가설 검증과 실패 (반복 구간)

이 단계가 글의 **가장 큰 볼륨**을 차지한다. 한 번의 시도가 아래 패턴으로 구성된다:

```
[가설 설명]
  → [어떤 설정/코드를 변경했는지 구체적으로]
  → [변경 후 결과 확인 (메트릭, 그래프, 에러 로그)]
  → [왜 이것이 근본 원인이 아닌지 논리적 분석]
  → [새로운 궁금증/가설로 이어지는 전환]
```

**핵심 포인트:**

- 시도마다 `#N` 넘버링을 붙인다 ("#1 커넥션 풀 옵션 수정", "#2 배포 전략 변경" 등)
- 실패한 시도도 **무엇을 배웠는지**를 반드시 정리한다
- 중간중간 독자에게 말을 건다: "여기까지 읽었을 때 여러분들의 생각은 어떤가요?"
- 가설이 틀렸음을 **데이터로 증명**한다 (30개→50개로 늘려도 여전히 모두 사용됨 → 커넥션 수 문제가 아님)
- 인용 블록으로 **문제 재정의** 순간을 강조한다

> 예시:
>
> > 커넥션이라는 리소스 자체 문제가 아니라, 생성된 직후 아직 모든 준비가 되지 않은 초기 파드로 들어오는 트래픽 유입량이 문제는 아닐까?

### 4단계: 진짜 원인 발견 — 아하 모먼트

- 여러 실패 시도에서 수집된 단서들을 **한데 모아 정리**한다 (번호 리스트)
- 메트릭 비교를 통해 병목 지점을 좁혀나가는 과정을 보여준다
- "배포 직후에만", "평소에는 5ms인데 직후에는 1s" 같은 **대비 데이터**가 핵심
- 원인을 찾는 과정을 **기술적 원리(이론)**로 뒷받침한다
- 이론 설명은 "JVM 기반 애플리케이션을 개발하거나 공부한 경험이 있으시면, 한 번씩 다 들어보셨을 내용입니다" 같은 **독자의 사전 지식을 존중하는 톤**으로 시작한다

### 5단계: 해결책 적용 — 구현과 검증

- 해결책의 코드를 보여주되, 핵심 로직만 간결하게 (주석 포함)
- 적용 전 기대 효과를 **번호 리스트로 3개 정도** 명시한다
- 적용 후 메트릭을 **Before vs After** 형태로 나란히 보여준다
- "트래픽이 더 늘어났음에도 불구하고 더 안정적이었습니다" 같은 성과 강조

### 6단계: 마치며 — 회고와 인사이트

- "지금 돌이켜보면 당연한 해결책이었을지 모르지만" 같은 겸손한 회고
- **과거의 나에 대한 솔직한 반성**: "처음에는 에러 로그에 꽂혀서 근본 원인을 파악하지 못하고 주변만 확인했다"
- 핵심 교훈을 한 문장으로 압축: "발생한 에러 로그는 문제에 대한 원인이 아니고, 증상일 뿐이었습니다"
- 비슷한 상황의 독자에게 조언
- "긴 글 읽어주셔서 감사합니다"로 마무리

## 말투와 톤 가이드

### 존댓말 기반 + 친근한 구어체

- 기본 어미: `~합니다`, `~습니다`, `~했습니다`
- 구어체 섞기: "네, 맞습니다", "궁금하시지 않나요?", "감을 잡으신 분들도 있고 아직 아리송하신 분들도 있으실 것 같습니다"
- **팀 단위 서술**과 **개인 서술**을 섞는다: "저희 팀은 ~했습니다" / "저 역시 ~했습니다"
- 기술적 설명에서는 좀 더 객관적 톤: "~라고 판단했습니다", "~라고 해석했습니다"

### 독자와의 대화 장치

- **직접 질문**: "여기까지 읽었을 때 여러분들의 생각은 어떤가요?"
- **공감 유도**: "감을 잡으신 분들도 있고 아직 아리송하신 분들도 있으실 것 같습니다"
- **호기심 자극**: "궁금하시지 않나요?", "도대체 ~ 무슨 일이 벌어지길래?"
- **사전 지식 존중**: "한 번씩 다 들어보셨을 내용입니다"

### 기술 용어 사용 원칙

- 영어 기술 용어는 **백틱(`` ` ``)으로 감싼다**: `connectionTimeout`, `maximumPoolSize`, `getConnection()`
- 핵심 키워드는 **볼드**로 강조한다: **JVM 웜업**, **커넥션 사용 시간**
- 처음 등장하는 개념은 한글 설명 + 영어 병기: "자바 가상 머신 (JVM)"
- 코드 블록에는 파일명이나 역할을 주석으로 명시한다

### 인용 블록(`>`) 활용 패턴

인용 블록은 두 가지 용도로 사용한다:

1. **당시의 사고/가설을 독백처럼 담을 때**

   > 커넥션 풀이 부족한 건가?

2. **참고 정보나 부연 설명을 본문과 분리할 때**
   > HikariCP wiki를 확인하면, 커넥션 풀 사이즈 계산에 대한 팁을 확인할 수 있습니다.

## 시각 자료 활용 규칙

1. **에러 로그 스크린샷**: 문제 발생 섹션 상단에 배치
2. **그라파나 메트릭 그래프**: Before/After를 나란히 보여주며, 각 그래프에 캡션 추가
3. **아키텍처 다이어그램**: 배포 파이프라인, 시스템 구조 설명 시 사용
4. **코드 블록**: 핵심 로직만 발췌, 주석으로 맥락 보충
5. 모든 이미지에는 **한 줄 캡션**을 붙인다: "증가하는 active 커넥션 개수"

---

## 섹션 제목 작성 규칙

- **메인 섹션** (`##`): 서술형으로, 내용을 함축한다
  - 좋은 예: "커넥션 타임아웃은 커넥션 문제가 아닐 수도 있다"
  - 나쁜 예: "커넥션 타임아웃 분석"
- **시도 섹션**: `#N` 넘버링 + 질문형/서술형 혼합
  - "#1 커넥션 풀 에러 로그 원인 해결을 위한 HikariCP 커넥션 옵션 수정"
  - "#2 트래픽 양이 문제일까? 배포 전략 변경을 통한 해결 시도"
- **서브 섹션** (`###`): 해당 섹션에서 다루는 내용을 명확히
  - "메트릭 분석을 통한 인사이트"
  - "모든 현상이 해석 가능해진 확실한 원인"

## 글쓰기 체크리스트

글 작성 후 아래 항목을 점검한다:

- [ ] **스포일러 먼저**: 서두에 결론을 한 줄로 밝혔는가?
- [ ] **실패 과정 포함**: 최소 1~2개의 실패한 시도가 포함되어 있는가?
- [ ] **데이터 근거**: 가설 검증/반박이 메트릭이나 로그 등 구체적 데이터로 뒷받침되는가?
- [ ] **독자 참여**: 중간에 독자에게 질문하거나 공감을 유도하는 문장이 있는가?
- [ ] **인용 블록**: 당시의 사고 과정이 인용 블록으로 생생하게 표현되었는가?
- [ ] **Before/After**: 해결 전후의 상태가 명확히 대비되어 있는가?
- [ ] **회고와 겸손**: 마무리에서 과거의 나를 돌아보며 교훈을 정리했는가?
- [ ] **인사**: "긴 글 읽어주셔서 감사합니다"로 끝맺었는가?

## 예시: 글 뼈대 템플릿

아래는 트러블슈팅 블로그 포스트의 뼈대 예시이다. 주제에 따라 유연하게 변형한다.

```markdown
# [제목: 문제를 해결하기 위한 여정 (feat. 해결 키워드)]

> 요약: [한 문장 요약]

## 시작하며

[자기소개] + [서비스 맥락] + [결론 스포일러] + [궁금증 유도] + [이 글에서 얻을 수 있는 것 리스트]

## 첫 에러 발생

[에러 로그/스크린샷] + [에러의 기술적 의미 분석] + [첫 번째 가설]

## #1 [첫 번째 시도 제목]

[가설] → [변경 내용] → [결과 확인] → [왜 안 되었는지 분석] → [새로운 궁금증]

## #2 [두 번째 시도 제목]

[가설] → [변경 내용] → [결과 확인] → [부분적 개선과 한계] → [문제 재정의]

## #3 [분석 심화]

[메트릭 종합 분석] → [진짜 병목 지점 발견] → [기술적 원리 설명]

## [해결책 적용]

[기대 효과] → [구현 코드] → [적용 후 메트릭 Before/After]

## [추가 궁금증 / 딥다이브]

[해결 이후 남은 궁금증 탐구] → [로그/데이터로 검증]

## 마치며

[회고] + [교훈] + [독자에게 조언] + [감사 인사]
```

## 비-트러블슈팅 주제에 적용하기

트러블슈팅이 아닌 주제(설계 결정, 기술 도입, 아키텍처 개선 등)에서도 핵심 원칙은 동일하다:

- **Why 중심**: "왜 이 기술을 선택했는가"의 사고 과정을 보여준다
- **대안 비교**: 고려했던 다른 옵션과의 트레이드오프를 서술한다
- **결과 검증**: 도입 후 실제 효과를 데이터로 보여준다
- **솔직한 한계 인정**: "아직 해결하지 못한 부분"을 밝힌다

## 제목 작성 패턴

카카오페이 블로그 제목은 아래 패턴 중 하나를 따른다:

1. **여정형**: "[문제]를 해결하기 위한 여정 (feat. [해결 키워드])"
2. **질문형**: "[기술명], 정말 다 알고 계신가요?"
3. **서술형**: "[서비스명]에서 [기술적 도전]을 [어떻게] 한 이야기"
4. **개발기형**: "[서비스/기능] 개발기: [핵심 내용 요약]"
5. **비유형**: "[비유적 표현] (with. [기술 키워드])"
